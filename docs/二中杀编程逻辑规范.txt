二中杀编程逻辑规范
==================

用途
----

本文件是 sanguosha 项目后续开发必须优先阅读的规则与程序设计规范。
以后新增或修改卡牌、装备、技能、阶段、响应、判定、伤害、濒死等逻辑前，
应先阅读本文件，再检查现有代码的状态机和结算上下文，不能只根据某一次画面
或单张卡牌写临时分支。

本项目暂不考虑身份、身份胜负奖惩和身份专属规则。其他基础规则、牌的结算、
装备效果和武将技能应尽量遵循标准官方规则。


请注意，所有代码必须是合理且可泛化的，新加入的东西是能融入现有体系框架的，能被现有概念解释的，而不是为了某个技能某个操作某个角色提供的特例！

一、核心术语必须分清
====================

1. 局

从游戏初始化开始，到满足胜负条件并结束为止，称为一局。

2. 轮

所有存活角色依次执行过一个回合，可视为一轮。规则文字写的是“回合”时，
不能擅自按“轮”实现。

3. 回合

一名角色从“回合开始”到“回合结束”的完整行动过程。一个标准回合有六个
阶段，顺序固定为：

准备阶段 → 判定阶段 → 摸牌阶段 → 出牌阶段 → 弃牌阶段 → 结束阶段

注意：

（1）标准规则是六个阶段，不是五个阶段。
（2）“准备阶段”即使当前没有默认动作，也必须在状态机中真实存在，因为
     以后会有“准备阶段开始时”发动的技能。
（3）“回合开始时”“阶段开始时”“阶段内”“阶段结束时”“回合结束时”
     是不同的触发时机，不能混为一个回调。
（4）跳过某阶段表示该阶段不执行，但不等于删除其他阶段，也不等于立即结束
     整个回合。

4. 使用、打出、弃置、失去、获得

这些动作不是同义词：

（1）使用牌：建立一次“使用牌事件”，通常包含使用者、牌、目标、次数限制、
     合法性检查、响应和效果结算。
（2）打出牌：为响应某个要求而打出，例如响应【杀】打出【闪】、响应
     【南蛮入侵】打出【杀】。打出通常不等于主动使用。
（3）弃置牌：牌因弃置动作进入弃牌堆。
（4）失去牌：牌离开角色的手牌区、装备区或其他所属区域。被获得、被弃置、
     被替换都可能构成失去。
（5）获得牌：牌进入角色手牌区。顺手牵羊装备牌时，原角色先失去装备，
     然后使用者获得该牌。
（6）牌或技能写有“视为使用或打出”时，必须由当前父事件决定动作类型：
     出牌阶段主动提交的是“使用”，须建立使用牌事件并检查次数、距离和目标；
     响应窗口提交的是“打出”，只满足当前响应要求，不得擅自计入主动使用次数。
（7）主动使用与响应打出可以复用合法牌选择组件，但不得共用未标明父事件类型
     的状态。取消、超时和结算回调必须返回各自父事件，主动操作绝不能落入
     “未打出响应牌”的伤害分支。
（8）任何因“弃置”进入弃牌堆的实体牌，都必须先以正面朝上的牌面移动到中央
     等待区并完成展示，再按当前结算节点统一清除。规则状态可以在动画开始前
     完成区域转移，但视觉上不得让弃牌从原区域直接消失。一次效果依次弃置
     多张牌时，必须逐张执行“选择／确定区域来源 → 移入中央等待区 → 动画完成”
     的子事件；前一张完成后才能开放后一张选择。各牌应在中央等待区保留各自
     的展示位置，直到该组弃置结算允许统一清除。此规范适用于弃牌阶段、技能
     代价、被技能弃置、装备离区后弃置及锦囊造成的弃置，不得为单张牌绕过。
（9）“视为使用或打出”的牌在满足响应后，必须进入与同名实体牌完全相同的
     后续结算入口。例如视为打出的【闪】与实体【闪】都应产生“杀被闪抵消”
     事件，并共同触发该事件之后的武器或武将技能；不得在转换技能分支中直接
     结束父结算。
（10）转换牌的牌名、属性和效果可以使用虚拟牌上下文，但中央等待区只展示
      实际被使用或打出的实体牌。若两张实体牌共同转换为一张虚拟牌，应展示
      两张实体牌，不能凭空绘制一张不存在的同名虚拟牌。

程序中必须记录动作原因，不能只写“从列表 A 删除，再加入列表 B”。建议牌
移动事件至少包含：

card、from_player、from_zone、to_player、to_zone、reason、source_event。

5. 伤害与失去体力

伤害和失去体力不是同一事件：

（1）伤害有来源、伤害牌、数值和属性，可被防止、增加、减少、传导，并可能
     触发“受到伤害后”等技能。
（2）失去体力通常没有伤害来源，不走伤害修正，不触发“受到伤害”。
（3）扣减体力后若体力值不大于 0，应进入濒死结算，而不是立即判定死亡。
（4）“受到伤害时”与“受到伤害后”是两个不同的伤害结算时机，不得共用
     AFTER_DAMAGE 或仅凭文字相近合并处理。
（5）伤害事件建立时必须保存六要素：渠道、属性、来源、受到伤害的角色、
     当前伤害值、是否为连环伤害。牌或技能、连环传导、伤害转移均建立独立的
     DamageEvent；连环或转移按规则继承原事件要素，不得只传递伤害数字。
（6）正式伤害结算前存在“伤害结算开始前”。若技能在这里把伤害替换为失去体力，
     不再进入伤害六时机，改走独立的失去体力与扣减体力事件。
（7）伤害结算的六个正式时机必须依次为：
     伤害结算开始时
     → 造成伤害时
     → 受到伤害时
     → 插入扣减体力事件
     → 造成伤害后
     → 受到伤害后
     → 伤害结算结束时。
（8）“造成伤害时”和“受到伤害时”均处于最终伤害值尚未确定的阶段。技能可以
     在这里增加、减少、防止或转移伤害；不得在进入这两个时机前冻结所谓
     “最终伤害值”。
（9）【藤甲】增加火焰伤害、【白银狮子】减少伤害和“当你受到伤害时”发动的
     武将技能属于同一个“受到伤害时”窗口。单个角色同一时机必须先处理武将
     技能，再处理装备技能，最后处理牌的操作或效果。因此角色同时拥有相关
     武将技和【藤甲】时，先询问武将技，再检查并触发【藤甲】。
（10）同一时机存在多个技能时，每个技能发动或执行完毕后必须重新检测事件、
      条件、次数、目标和技能是否仍有效。前一个技能若防止全部伤害、转移伤害
      或令当前时机结束，后面的技能失去本次发动机会；不得在进入时机时一次性
      收集候选后无条件全部执行。
（11）若伤害在“伤害结算开始时”“造成伤害时”或“受到伤害时”被防止或减为0，
      视为来源没有造成过伤害、目标没有受到过伤害。跳过扣减体力、造成伤害后
      和受到伤害后，但仍进入“伤害结算结束时”；不得把整个事件直接删除。
（12）最终伤害值只有在“受到伤害时”全部结束且伤害仍存在后才确定。随后插入
      扣减体力事件，依次处理扣减体力前、扣减体力时、实际扣减、必要时插入
      濒死/死亡、扣减体力后。濒死结算完成后才返回未完成的伤害事件。
（13）扣减体力事件完成后，先处理“造成伤害后”，再处理“受到伤害后”。
      “受到伤害时”产生的回复先改变体力，再承受本次最终伤害；“受到伤害后”
      的技能只能在扣体力及必要的濒死结算完成后检查。
（14）“当你造成/受到伤害时或后”默认按一次 DamageEvent 提供一次机会，不按
      伤害点数拆分。只有技能明确写“每造成/受到1点伤害”或其他按点计数文字时，
      才按最终伤害值提供相应次数。
（15）角色确实在连环状态下受到属性伤害时，只记录“须重置”和“须触发连环”
      条件；到“伤害结算结束时”才重置，整个伤害事件结束后才触发连环。
      连环中的每个目标分别建立新的伤害事件并完整经历六时机，不能批量扣血。
（16）多名角色在同一时机可以响应时，从当前回合角色开始按行动顺序依次处理；
      单个角色同时有多个同类武将技能时由其决定顺序。每次轮到技能前重新校验，
      若先发动的技能令时机消失，后续角色或技能不得继续发动。


二、六个阶段的状态机规范
========================

每个阶段都应遵循统一生命周期：

进入阶段前
→ 阶段开始时
→ 执行阶段默认动作或玩家操作
→ 阶段结束时
→ 离开阶段

任何阶段推进只能由当前阶段唯一的完成回调触发一次。动画、AI 延时、响应窗口
和判定展示的旧回调必须带有阶段令牌或结算令牌；令牌失效后不得再次推进阶段。

1. 准备阶段

默认动作：无。

主要用途：

（1）结算“准备阶段开始时”的技能。
（2）为以后加入观星、洛神等技能保留合法触发窗口。
（3）所有可选技能询问完成后，才进入判定阶段。

禁止做法：

不能因为默认动作为空就在 Phase 枚举中省略准备阶段。

2. 判定阶段

默认动作：依次结算当前角色判定区里的延时锦囊。

逻辑要求：

（1）先确定本次要结算的延时锦囊。
（2）建立延时锦囊结算上下文。
（3）若允许【无懈可击】，先完整结算无懈响应链。
（4）效果仍有效时才进行判定。
（5）亮出牌堆顶的判定牌，建立判定事件。
（6）开放“判定牌生效前”的改判窗口。
（7）改判全部结束后确定最终判定结果。
（8）执行延时锦囊结果并移动相关卡牌。
（9）完成一张后再处理下一张。
（10）判定区清空或全部处理完毕后，才能进入摸牌阶段。

判定牌必须进入处理区或等价的临时区域，判定完成后再进入弃牌堆。不能在结果
尚可能被修改时提前当作最终牌弃置。

3. 摸牌阶段

默认动作：当前角色摸两张牌。

逻辑要求：

（1）先处理“摸牌阶段开始时”的技能。
（2）确定本次摸牌数量，允许技能替换或修改。
（3）执行摸牌。
（4）处理因获得牌触发的事件。
（5）完成所有嵌套事件后才结束摸牌阶段。
（6）一次“摸N张牌”只能建立一个 DrawCardsEvent。事件必须记录稳定 draw_id、
     摸牌角色、实际张数、全部实体牌、原因、来源事件和对应移动编号；不能把
     摸两张拆成两次摸一张。以后“当一名角色一次摸超过一张牌时”等技能直接
     检查该事件的 count，不得通过同一帧出现几张动画或手牌增量反推。
（7）同一次摸牌产生的各张 CardMoveEvent 共享 batch_id，并保存 batch_index
     与 batch_size。它们在规则上仍是各自独立的实体移动，但属于同一个不可
     拆分的摸牌动作。

若角色跳过摸牌阶段，则不执行默认摸两张，但仍须按统一状态机安全地进入下一
阶段，不能遗留摸牌动画或旧定时器。

4. 出牌阶段

默认动作：由当前角色在空闲时间点反复选择合法行动，直到主动结束出牌阶段
或被效果结束。

每次行动必须按以下顺序：

（1）玩家选择牌或技能。
（2）选择目标和附加参数。
（3）统一检查使用合法性，包括牌是否仍在原区域、目标是否存活、距离、
     攻击范围、次数限制、目标数量和禁止效果。
（4）合法后才提交行动并移动牌。
（5）建立使用牌事件并完整结算。
（6）包括响应、伤害、濒死、死亡、连环和后续技能在内的所有嵌套结算结束后，
     才重新回到出牌阶段的空闲时间点。

禁止做法：

（1）卡牌动画尚未完成就允许再次出牌。
（2）上一次响应队列未清空就覆盖全局 response_card_name。
（3）先从手牌永久移除，发现目标非法后却无法原位恢复。
（4）把“每回合一次”错误实现成“每个出牌阶段一次”，或反过来。

5. 弃牌阶段

默认动作：若手牌数大于当前手牌上限，当前角色必须弃置超出的手牌。

基础手牌上限通常等于当前体力值，但应通过统一 hand_limit(player) 接口计算，
以便技能修改。

逻辑要求：

（1）进入弃牌阶段时计算当前需要弃置的数量。
（2）玩家选择的必须是可弃置的手牌。
（3）提交前重新计算，防止嵌套技能改变体力或手牌数。
（4）执行弃置事件和相关触发。
（5）若触发后仍超上限，应按规则判断是否继续要求弃牌。
（6）全部结算完成后进入结束阶段。

6. 结束阶段

默认动作：无。

主要用途：

（1）结算“结束阶段开始时”和“结束阶段结束时”的技能。
（2）清除明确写明持续到本回合或本阶段结束的临时标记。
（3）结束阶段全部结算后，再处理“回合结束时/回合结束后”的事件。
（4）最终切换到下一名存活角色。

禁止在进入结束阶段的一瞬间就清空所有标记。有些技能需要在结束阶段内读取
本回合统计数据，应在对应触发窗口结束后再清理。


三、事件、响应窗口与嵌套结算
============================

1. 总原则

二中杀不是一串互不相关的按钮回调，而是事件驱动的嵌套结算系统。

新事件可能在旧事件尚未结束时产生。例如：

使用一张牌
→ 创建目标效果
→ 目标进入响应窗口
→ 响应中发动一个可选技能
→ 技能产生判定事件
→ 判定中产生改判事件
→ 改判和判定依次结束
→ 恢复响应事件
→ 响应结束后恢复目标效果
→ 原使用牌事件结束
→ 返回出牌阶段空闲时间点

程序必须暂停父事件，完整处理子事件，子事件完成后准确恢复父事件。不能依赖
一组会被覆盖的全局变量保存所有上下文。

2. 结算帧

每个可暂停的事件应建立独立结算帧，建议包含：

event_id
event_type
source_player
target_players
current_target
source_card
required_response
effect_active
step
parent_event_id
continuation
temporary_data

结算帧压入栈后，只有栈顶事件能接受输入。子事件结束时弹栈，并调用父事件
保存的 continuation。不得让子事件直接猜测父事件下一步是什么。

3. 栈与队列的分工

（1）栈用于“事件中插入事件”的嵌套：
     无懈链、判定、改判、伤害、濒死、求桃、技能询问。

（2）队列用于“同一层级多个对象依次处理”：
     南蛮入侵逐个目标、万箭齐发逐个目标、桃园结义逐个角色、铁索连环多个
     目标、多人依次求桃。

（3）队列中的某个目标产生子事件时，暂停队列；子事件全部完成后，才取下一
     个目标。

（4）不能在进入子事件时清空父队列。若必须复用当前字段，应把完整父上下文
     压栈，恢复时原样还原。

4. 同一时机多个事件

若同一时机有多个角色或多个技能可处理：

（1）先收集合法触发项，不能边扫描边执行导致后续条件被意外跳过。
（2）按规则确定顺序；涉及多名角色时，项目统一从当前回合角色开始按座次
     顺序处理。
（3）同一角色有多个可选技能时，应让该角色选择顺序；AI 可按策略排序。
（4）每处理一项后重新检查剩余项是否仍然合法。

5. 多目标牌

一张牌指定多个目标时：

（1）“使用一张牌”只有一个父事件。
（2）每个目标有独立的目标效果结算。
（3）目标 A 的响应和伤害全部结束后，再处理目标 B。
（4）某目标的效果被无懈或防具取消，不代表整张牌对其他目标失效。
（5）目标在轮到自己前死亡或失去合法性时，应跳过该目标并继续队列。

6. 无懈可击

【无懈可击】是嵌套响应链，不是简单布尔值：

（1）对某个锦囊的某个目标建立无懈窗口。
（2）一张无懈可被另一张无懈响应。
（3）每成功结算一张无懈，原效果的有效状态翻转一次。
（4）所有角色连续放弃响应后，才确定最终状态。
（5）只取消当前目标的效果时，不得清除多目标牌的剩余目标队列。

7. 伤害与濒死

伤害事件推荐顺序：

建立伤害事件
→ 确定来源、伤害牌、初始数值和属性
→ 伤害即将造成的增加/减少/防止效果
→ 扣减体力
→ 若体力不大于 0，立即插入濒死事件
→ 求桃/酒响应
→ 脱离濒死或死亡
→ 伤害后触发
→ 属性伤害的连环后续
→ 返回父事件

需要特别注意：

（1）白银狮子限制的是每次伤害的最终数值，每个连环传导目标都要单独经过
     自己的防具和伤害修正。
（2）藤甲受到火焰伤害时，每次独立伤害增加 1 点。
（3）铁索传导产生新的目标伤害事件，但保留原伤害来源和属性，并标记为传导，
     防止再次无限生成同一批传导。
（4）濒死是伤害事件内部插入的子事件。濒死未结束前不能继续下一目标。
（5）体力值不大于 0 不等于已经死亡；求救全部失败后才死亡。
（6）决斗等多轮交替响应每进入新一轮，都必须重新绑定同一个父结算的成功续接；
     实体牌、虚拟牌和转化牌响应成功后必须进入相同的下一轮，不得依赖只覆盖
     实体牌路径的界面特判。


四、通用判定事件设计规范
========================

1. 判定不是判定阶段的专属动作

“判定阶段”是回合的六个阶段之一；“进行判定”则是一种可以在任何合法时机
插入当前结算的事件。两者必须分开建模。

判定可能来自延时锦囊、牌的使用或响应、装备或武将技能、伤害前后、阶段触发
以及其他事件的后续效果。因此，程序不得限制只有 Phase.JUDGE 才能调用判定，
也不能让通用判定函数自动推进判定阶段。

通用判定事件只负责完成本次判定并把结果返回父事件；是否推进阶段、继续响应
或执行伤害，必须由创建判定的父事件决定。

2. 每次判定必须有独立上下文

建议统一使用 JudgmentEvent，至少保存：

judgment_id：本次判定的唯一编号
judging_player：进行判定的角色。A发动八卦阵产生判定，或A在自己的判定阶段
结算判定区里的牌，均记录A；不得记录攻击者、延时锦囊的使用者或改判者。
reason：判定原因或来源技能
source_player：引发判定的角色，可为空
source_card：引发判定的牌，可为空
parent_event_id：父结算事件
initial_card：最初亮出的判定牌
current_card：当前有效的判定牌
replaced_cards：被改判替换掉的判定牌
result_rule：如何根据最终判定牌计算结果
result：冻结后的最终判定结果
step：当前结算步骤
continuation：判定完成后恢复父事件的回调

不能只用一个全局 judged_card 保存判定牌。判定中插入技能询问、改判、伤害或
另一项事件时，全局字段容易被覆盖，使父事件读取到错误结果。

3. 标准判定流程

创建 JudgmentEvent
→ 暂停父事件
→ 从牌堆顶取得一张牌
→ 将牌正面朝上置入处理区
→ 记录 initial_card 和 current_card
→ 广播“判定牌生效前”事件
→ 收集并依次处理合法改判机会
→ 每次改判后更新 current_card
→ 所有人均不再改判后冻结最终判定牌
→ 按 result_rule 计算最终结果
→ 广播“判定结果确定”事件
→ 处理参与本次判定的牌的最终去向
→ 完成 JudgmentEvent
→ 恢复父事件的 continuation，并把结果传回父事件

父事件不得在判定结果冻结前提前执行成功或失败分支。

4. 判定牌、判定区与处理区

（1）判定过程中亮出的牌属于处理区，不属于任何角色的手牌、装备区或判定区。
（2）判定区存放等待结算的延时锦囊，不是本次亮出的判定牌。
（3）判定牌进入处理区时必须从牌堆移除，不能同时存在于牌堆和画面中央。
（4）判定尚未结束时，不能提前把 current_card 加入弃牌堆。
（5）通常在判定完成后，最终判定牌和被替换的旧牌进入弃牌堆。
（6）若技能明确获得、置于牌堆顶、置于武将牌上或改变去向，应由牌移动事件
     覆盖默认弃置去向。
（7）每张实体牌只能有一个最终区域，禁止重复弃置或同时被两名角色获得。

建议统一使用 DRAW_PILE、DISCARD_PILE、HAND、EQUIPMENT、JUDGMENT_AREA、
PROCESSING 等区域标识。

5. 判定结果只读取最终有效牌

所有成功或失败条件只能读取改判结束后的 current_card。公共判断至少包括：

（1）颜色：红色为红桃或方块；黑色为黑桃或梅花。
（2）花色：spade、heart、club、diamond。
（3）点数：A=1，J=11，Q=12，K=13，其余使用数字点数。
（4）牌名或类别：仅在规则明确要求时读取。

禁止在业务函数里重复编写不同版本的颜色或点数换算。应统一提供 is_red、
is_black、rank_value 和 matches_judgment 等接口。

result_rule 应为结构化条件或可测试函数，不能依赖 UI 提示文字判断结果。

6. 改判是判定中的嵌套响应窗口

改判不是重新创建一场无关判定，而是修改同一个 JudgmentEvent 的 current_card。

（1）亮出初始判定牌后，创建改判响应窗口。
（2）按当前回合角色起始的座次顺序询问具有合法改判能力的角色。
（3）同一角色有多个合法改判方式时，由该角色选择。
（4）改判技能含“可以”时，必须显示确定/取消或选择牌窗口。
（5）改判技能为锁定效果时，满足条件后自动执行。
（6）提交改判时重新检查技能、牌所在区域和动作合法性。
（7）改判完成后更新 current_card，记录旧牌与新牌的移动原因。
（8）规则允许继续改判时，应基于新的 current_card 继续询问。
（9）所有改判窗口结束后才冻结结果。

程序不能在第一次有人改判后立即执行判定结果，除非规则明确不能继续改判。

7. 判定中再次插入事件

判定过程中可能插入技能询问、弃牌、获得牌、伤害或濒死：

（1）保留完整 JudgmentEvent 作为父结算帧。
（2）将新事件压入结算栈。
（3）新事件完成后恢复原 judgment_id 和 step。
（4）恢复时重新检查 owner 是否存活、技能是否有效、牌是否仍在预期区域。
（5）拥有者在嵌套事件中死亡时，根据具体规则决定终止还是继续；不能无条件
     执行原成功分支。
（6）动画和定时回调必须校验 judgment_id，不能修改另一场判定。

若效果要求重复或继续判定，每次翻牌都应创建新的 JudgmentEvent，通过父级
循环或队列串联，不能复用上一场判定的 current_card 和改判状态。

8. 多个判定必须串行

（1）判定区有多张延时锦囊时，一张完整结算结束后再处理下一张。
（2）同一时机触发多个判定时，先确定顺序，再逐个创建判定事件。
（3）不得同时翻开多张判定牌后再分别开放改判窗口。
（4）前一判定及其全部嵌套事件结束后，后一判定读取最新牌堆状态。
（5）多名角色依次判定使用队列；单次判定内部的改判使用结算栈。

9. 牌堆耗尽与洗牌

判定取牌必须复用统一牌堆接口：

（1）取判定牌前牌堆为空时，按项目规则重洗弃牌堆。
（2）处理区里的牌不能参与本次重洗。
（3）本次判定中尚未确定去向的牌不能提前进入重洗集合。
（4）牌堆和可重洗弃牌堆均为空时，应产生明确异常或终局处理，不能返回 None
     后继续按某种花色结算。

10. UI、动画与 AI

UI 应展示判定原因、进行判定的角色、当前判定牌、改判询问和最终结果。
动画只负责展示牌的移动；规则状态由引擎提交。动画回调必须携带 judgment_id，
且只能推进同一判定一次。

所有判定都必须进入统一的可视化流程，不得只在判定阶段展示。无论判定来自
判定区里的延时锦囊、装备技能、武将技能、牌的效果、响应过程或伤害过程，
均须：

（1）在判定开始时显示判定原因和进行判定的角色。
（2）将最终有效判定牌正面朝上移动到中央等待区。
（3）在改判尚未结束时持续展示当前有效判定牌，不得提前显示成功或失败。
（4）最终结果冻结后，明确提示牌的花色、点数以及“生效、未生效、成功、
     失败、视为使用或打出某牌”等实际结果。
（5）判定牌和结果至少停留统一的 JUDGMENT_RESULT_HOLD_MS 展示时间。
（6）展示期间暂停父响应计时、出牌计时和阶段推进。
（7）展示完成后清理中央判定牌，再按 continuation 恢复原父结算。
（8）阶段外判定不得因复用展示流程而错误进入、结束或推进判定阶段。
（9）真人和 AI 产生的相同判定使用完全相同的展示流程。

不得出现“日志已经写出判定结果，但中央等待区没有判定牌”“判定牌一闪而过
没有结果提示”或“结果提示结束前父事件已经继续结算”的情况。

最终结果展示结束前，父事件保持暂停。展示结束后 continuation 只能调用一次。

AI 不得绕过 JudgmentEvent 直接修改牌堆结果。AI 只能读取已经公开的判定牌，
从引擎提供的合法改判动作中选择，并通过与真人相同的接口提交。

需要按顺序指定多种角色身份的牌或技能，必须维护一个尚未提交的选择上下文：
先依次记录每种身份的合法选择，最后只由一次明确的【确定】提交完整行动。选择
中间目标时不得提前移牌、播放出牌音效、写入“已经使用”的日志或开始结算；点击
【取消】应退出当前选择并保持规则状态不变。最终确定时必须重新校验所有目标。
例如【借刀杀人】的真人流程统一为“选择牌 → 指定持刀者 → 指定被【杀】者 →
点击确定 → 提交并执行”，持刀者和被【杀】者必须作为同一行动的两个不同目标
一起校验，不得在选择第二目标时自动提交。

一张牌需要用多段箭头表达不同关系时，每段箭头的起点、终点、开始时间和段间
停顿必须显式记录在同一个动画上下文中。段间停顿属于表现参数，不得通过阻塞
规则状态或提前开始后续结算来实现；最后一段动画和统一停留结束后才能恢复结算。

敌方武将牌旁不得常驻显示技能操作框，避免把敌方公开资料误画成可由本地玩家
点击的操作入口。武将资料统一采用悬停查看：鼠标在当前实际显示的任意武将牌
区域内连续停留满1秒后，显示武将名、势力、体力和全部技能说明；敌我武将使用
同一套浮层。鼠标一旦移出该武将牌区域，浮层和本次计时立即消失；移动到另一名
武将时必须重新计时。

悬停框中的技能名、技能类型和规则文字必须按稳定 skill_id 从统一
SkillDefinition 读取，不得在界面代码中复制技能描述，也不得因技能属于敌方而
隐藏公开信息。新增技能时，标准技能描述必须与规则定义一同登记，悬停界面只做
只读展示，不得改变技能有效性或产生任何操作按钮。

武将的选中、行动中、响应中、濒死等状态框必须共用统一的外扩绘制规则。状态框
的可见边线应落在武将牌边界之外，不得压住边框内的势力字、竖排姓名、体力或
其他牌面信息；新增状态框也必须经过同一入口，不能为某一种颜色或状态单独调整。

主界面右上角必须提供常驻【退出】按钮，并与窗口关闭事件、Esc键共用同一个退出
请求入口。退出按钮在普通对局、选择或响应提示、动画期间以及游戏结束画面均可
使用；它只结束客户端运行，不得先提交当前选择、推进结算或改写胜负状态。

中央等待区上方应保留独立的技能发动提示层。只有技能已经通过合法提交或锁定技
实际介入结算后，才能显示“【角色】使用了技能【技能名】”；仅打开询问、进入
选牌、悬停技能、取消发动、非法提交或技能最终未生效时均不得显示。提示使用
统一技能定义中的名称，不得从日志文字反向猜测。

该黄字提示专用于武将技能。武器、防具和坐骑的效果即使在底层按统一技能接口
注册，也只播放对应装备音效和表现动画，不显示“使用了技能”黄字；不得把
【麒麟弓】等装备名称当作武将技能名展示。

本地手牌区上方的操作提示只服务于当前需要本地玩家完成的操作。询问敌方发动
技能、响应、选牌或执行行动时，只显示敌方一侧的决策进度，不得把敌方询问文案
画到我方进度条或手牌区上方；轮到本地玩家响应敌方行动时才恢复本地操作提示。

游戏创建玩家和发初始手牌前必须先完成独立选将阶段。候选池只能来自 playable
为真的已完整实现武将，随机展示至多八名，并按每行至多四张排列。各座位严格按
座次依次选择且不得重复；已选武将仍保留在公共候选区中，但必须灰暗并禁止再次
选中。真人只提交自己当前座位的点击选择，AI只从尚未被选择的候选武将中随机
选择。所有座位完成后，才按座次结果创建Player、GameEngine并开始发初始手牌。

技能提示以黄字完整显示2秒，随后进行统一淡出。任一新技能在旧提示停留或淡出
期间实际发动时，新提示必须立即覆盖旧提示并从零重新计时；不建立排队，也不让
旧提示的淡出回调清除新提示。该提示仅属于表现层，不阻塞动画、响应计时或规则
结算。中央等待区及所有等待牌动画落点必须共用同一布局常量，移动等待区时不能
只移动背景而遗漏牌、判定或其他飞牌终点。

11. 判定测试最低要求

每个产生判定的功能至少测试：

（1）无改判时使用初始判定牌得到正确结果。
（2）颜色、花色和 A/J/Q/K 点数换算正确。
（3）可选判定或可选改判的确定、取消和超时。
（4）一次和多次改判后只使用最终有效牌。
（5）初始牌、替换牌和最终牌区域正确，没有重复牌。
（6）牌堆为空时正确重洗，处理区牌不参与重洗。
（7）判定中插入其他事件后能恢复正确父事件。
（8）连续判定严格串行，不共享 current_card。
（9）拥有者死亡或技能失效时不会执行过期回调。
（10）判定完成后 continuation 只调用一次。
（11）判定阶段外发起判定时，不会错误推进当前回合阶段。
（12）真人和 AI 使用同一规则接口并得到一致状态。


五、锁定技、一般技能与“可以”
============================

1. 锁定技

牌面明确写“锁定技”，或规则明确规定为强制生效的效果，不询问玩家是否发动。

程序特征：

（1）条件满足时自动执行。
（2）不显示“是否发动”的确定/取消窗口。
（3）必须在规定时机执行，不能因玩家超时或 AI 选择而跳过。
（4）仍需记录日志，说明是哪个锁定技修改或取消了事件。

示例：

（1）仁王盾：黑色【杀】对装备者无效。满足条件时自动令该【杀】无效。
（2）藤甲：南蛮入侵、万箭齐发和普通【杀】无效；火焰伤害增加 1。
     均自动生效。
（3）白银狮子：每次受到的伤害最多为 1；失去装备区里的白银狮子时回复
     1 点体力。条件满足时自动生效。

2. 一般技能和可选效果

描述中有“可以”“可”“你令……”且未声明锁定的效果，默认需要拥有者决定
是否发动。

程序特征：

（1）条件满足时创建 SkillPrompt/技能询问事件。
（2）保存询问前的父结算上下文。
（3）显示技能名称、触发原因、确定和取消按钮。
（4）点击确定才支付消耗、选择目标或执行判定。
（5）点击取消表示本次触发不发动，返回原事件的下一合法步骤。
（6）超时行为应明确配置，通常按取消处理，不能默认替玩家发动可选技能。
（7）AI 也必须经过同一事件接口，只是由策略函数代替按钮选择。

3. “你可以”的程序含义

“你可以做 X”必须拆成两步：

第一步：询问是否发动。
第二步：玩家确认后才做 X。

错误实现：

条件满足 → 自动执行 X → 只让玩家接受结果。

正确实现：

条件满足
→ 暂停父结算
→ 显示“是否发动”
→ 确定：执行 X
→ 取消：不执行 X，恢复父结算

4. 技能失效与防具无效

以后加入“防具无效”“技能失效”时，统一在触发条件检查中处理：

（1）先判断装备是否存在且有效。
（2）无效的装备不创建锁定效果，也不创建可选询问。
（3）不能先执行装备效果，再用另一个标记把结果改回去。
（4）青釭剑等令防具无效的效果应有明确持续范围，只影响规定的【杀】事件。

5. 技能来源与发动者

技能不能只按“武将技能”或“装备效果”写死分支。统一 SkillDefinition 至少记录：

skill_id、name、source_type、owner、controller、timing、mandatory、cost、
target_rule、usage_limit、effect、priority_group、invalidity_scope。

source_type 至少区分：

（1）GENERAL：武将牌提供的技能。
（2）WEAPON：武器牌提供的装备技能。
（3）ARMOR：防具牌提供的装备技能。
（4）MOUNT：坐骑牌提供的装备技能。
（5）TREASURE：宝物牌提供的装备技能。
（6）TEMPORARY：由牌、标记或其他技能临时授予的技能。

owner 是技能归属者；controller 是本次负责决定是否发动、选择牌或选择目标的
操作者。两者通常相同，但规则文字明确让其他角色选择时必须分开。

操作者按技能文字确定：

（1）“你可以……”：技能拥有者操作。
（2）“其可以……”或“令其选择……”：文字所指角色操作。
（3）武器技能通常由武器装备者操作，不能由【杀】的目标操作。
（4）防具技能通常由防具装备者操作。
（5）响应技能由当前被要求响应的角色操作。
（6）改判技能由拥有改判能力且处于当前询问顺序的角色操作。
（7）AI 控制的角色仍是 controller，AI 只替代输入方式，不改变规则归属。

6. 按操作方式划分技能

（1）主动技：在规则允许的空闲时间点由操作者主动发起，一般需要选择技能、
     支付消耗并选择目标。未点击技能按钮时不自动发动。
（2）触发技：指定事件和时机出现后进入触发候选列表。含“可以”时询问，
     强制时自动执行。
（3）锁定技：满足条件必须发动或产生效果，其唯一特殊性是强制性。
（4）牌的转化或“视为”是效果机制，不是与锁定技、一般技能并列的发动
     类型。含此机制的技能仍按文字判断其是否为锁定技；未写“锁定技”的，
     按非锁定技处理并由操作者自主选择。实现时必须检查当前窗口是否允许
     使用或打出转化后的牌，但不得把“发生转化”误写成名为“转换技”的
     官方技能类型。
（5）状态技/持续效果：在有效区间内修改距离、次数、目标或伤害等规则，
     不应每帧重复执行动作。
（6）限定技、觉醒技等带标记技能：除自身发动条件外，还必须通过持久标记记录
     是否已经使用或完成；不能只靠按钮隐藏。

“锁定技”不是高于其他技能的优先级类型。官方规则中，锁定技除必须发动或
产生效果外没有额外优先权；结算顺序仍由准确时机和多事件结算原则决定。

7. 规则文字中“牌”的区域解释

（1）文字写“你的牌”“一张牌”且没有进一步限定区域时，候选实体统一为
     该角色的手牌和装备区里的牌。
（2）文字明确写“手牌”“装备区里的牌”“判定区里的牌”时，只能从所写
     区域选择，不得自行扩大或缩小范围。
（3）此解释属于通用规则，不得在某一个武将技能或装备效果中作为特例硬编码。
     应由统一的区域候选接口产生候选牌，再叠加颜色、花色、类别等条件。
（4）牌一旦作为技能代价、转化实体或被使用/打出，必须从其真实原区域移动。
     装备牌离开装备区时照常触发“失去装备区里的牌”及装备离区效果。
（5）处理区、判定区和牌堆中的牌不属于“你的牌”；只有规则文字明确包含这些
     区域时才可作为候选。

技能按钮能否使用与转化材料能否支付必须分层判断：

（1）技能按钮的可用状态检查转化后的牌或操作在当前窗口是否合法。例如将牌
     当【杀】使用时，应检查当前阶段是否允许使用【杀】、使用次数是否达到
     上限、是否存在合法目标及其他针对【杀】的限制。
（2）操作者当前是否拥有满足颜色、花色、类别或数量要求的实体牌，不属于技能
     按钮能否使用的检测范围，不得因此提前将技能按钮置灰。
（3）玩家点击技能后进入选牌或支付步骤，再由候选区域接口标明哪些实体牌可选；
     没有合适实体牌时，玩家仍可取消技能操作，不产生使用次数或其他消耗。
（4）提交技能时必须同时复核转化后牌的使用合法性和所选实体牌的支付合法性，
     防止嵌套结算导致按钮点击后状态变化。

装备牌参与使用、打出、转化或支付时，必须采用“先离区、后求值”的有效性快照：

（1）若某张装备牌本身是本次被使用、打出、转化或支付的实体牌，则计算本次
     行动的合法性和效果时，视为该装备已经不在装备区。
（2）该装备不能既作为本次行动的实体牌或代价，又为同一次行动提供攻击范围、
     使用次数、防具无效、额外目标、伤害修正等装备效果。
（3）合法性预览不得真的提前移动装备，而应把“本次将离区的装备牌集合”作为
     excluded_cards/离区快照传给次数、距离、目标和效果查询接口。
（4）例如角色本阶段已经使用过【杀】，即使当前装备【诸葛连弩】，也不能再将
     这张【诸葛连弩】本身转化为【杀】并同时利用其不限次数效果。选中该装备后，
     应按失去连弩后的状态重新判断，所有非法目标置灰且不能提交。
（5）同理，将武器转化或支付后，其攻击范围不适用于该次牌；将青釭剑转化后
     不能令该次【杀】无视防具；将方天画戟转化后不能为该次【杀】增加目标。
（6）最终提交时再按同一离区快照复核，随后才执行真实区域移动和装备离区事件。

需要使用或打出牌的响应窗口与牌转化技能必须共用一个响应界面：

（1）父事件只创建“需要使用或打出【某牌】”的统一 ResponseWindow，不得因为
     角色拥有武圣、丈八蛇矛等牌转化能力，就在正常响应前逐个询问是否发动。
（2）响应界面直接允许选择符合要求的实体牌；同时把当前窗口中可操作的转化
     技能按钮或装备入口设为可操作状态。
（3）玩家点击转化技能后，才进入该技能的实体牌选择步骤；取消该步骤应返回
     原 ResponseWindow，仍可选择实体牌、其他转化技能或放弃响应。
（4）转化技能是否能进入当前响应窗口，只检查转化后的牌名和动作类型是否满足
     required_card、use/play 要求及其他窗口限制，不因当前缺少转化材料而隐藏
     或提前弹出询问。
（5）AI 使用同一个 ResponseWindow 和合法动作集合，只由策略选择实体牌响应、
     某项转化动作或放弃，不得另写自动询问链。
（6）八卦阵等在“需要牌”时另外产生判定或其他独立效果的可选触发技能，仍按
     其准确时机建立是否发动询问；它不属于选择实体牌进行转化的操作。
（7）响应提示不得在 main.py 或 UI 中枚举武将名、技能名或 skill_id。统一由
     SkillRuntime 根据响应者当前实际拥有且有效的技能返回
     ResponseConversionOption 列表；UI 只遍历列表生成提示和入口。没有对应
     选项时使用完全通用的“请选择/使用/打出【某牌】或取消”提示。

8. 主动操作与询问窗口

玩家可自主操作的情况至少包括：

（1）出牌阶段空闲时间点发动主动武将技能或主动装备技能。
（2）某事件触发了含“可以”的武将、武器、防具或临时技能。
（3）需要使用或打出牌时，选择合法的视为技或转换技。
（4）同一时机有多个本人可发动技能时，选择发动哪一个以及顺序。
（5）技能需要牌、目标、选项或数值时，选择合法参数。

统一询问流程：

发现触发条件
→ 检查技能来源仍存在且有效
→ 检查次数、消耗、目标和父事件仍合法
→ 创建 PromptContext
→ 暂停父结算
→ controller 选择确定、取消或具体合法动作
→ 确定后再次校验
→ 支付消耗并锁定所选参数
→ 创建技能结算事件
→ 技能结算结束后恢复父事件

提示至少显示：技能名、来源、触发原因、需要支付的消耗、合法目标或选项，
以及确定/取消的准确含义。不得用同一全局布尔值猜测按钮属于哪个技能。

对于主动技，玩家尚未提交前不支付消耗。对于触发技，点击取消或超时按本次
不发动处理。锁定技不创建是否发动提示，但若效果本身要求选择目标或选项，
仍应创建“选择如何执行”的强制提示；此提示不能通过取消来逃避必须执行的部分。

8. 武器技能的专门规划

武器装备到装备区后注册对应技能，离开装备区后注销。武器技能不得散落在
各张【杀】的按钮回调中。

武器技能通常依附于一次使用【杀】事件，应保存：

weapon_card、wielder、slash_event_id、slash_card、current_target、
timing、paid_cost、effect_scope。

实现时区分：

（1）锁定或持续修改：攻击范围、用【杀】次数、伤害属性转换等，在合法性或
     对应修正窗口自动计算。
（2）可选触发：指定目标后、目标使用【闪】后、即将造成伤害时、造成伤害后
     等准确时机询问装备者。
（3）需要弃牌或选择目标的武器技能，确认后才支付消耗；支付失败则不能发动。
（4）武器在技能询问或结算中离开装备区时，重新判断该技能是否还能继续。
（5）某次【杀】令防具无效时，作用域必须绑定该 slash_event_id 和目标，
     不能永久修改目标防具。

9. 武将技能的专门规划

9.1 武将、角色与技能不是同一对象

武将牌 General 是开局候选模板，至少保存 general_id、名称、势力、体力上限
和技能引用。角色 Player 是选将确认后进入本局的运行时对象，保存座次、当前
体力、区域、状态、操作者及所选武将。SkillDefinition 是技能规则定义。

禁止把“选择了某武将”“角色当前拥有某技能”“该技能此刻有效”“该技能本次
已经发动”合并成一个布尔值。四者应分别由：

selected_general
owned_skill_ids
is_skill_effective(...)
SkillEvent/usage_marker

表示。

9.2 开局选将与绑定流程

项目暂不考虑身份，但以后加入选将时必须使用以下流程：

加载并校验武将数据
→ 按对局配置生成候选武将池
→ 为每名玩家建立选将 PromptContext
→ 玩家或 AI 提交 general_id
→ 重新验证该武将仍在其合法候选集合
→ 创建 Player，并写入所选 General
→ 由 General.skills 的 skill_id 建立角色初始技能来源
→ 初始化体力上限、当前体力和技能局内标记
→ 所有人选将完成后进入“游戏开始前/游戏开始时”事件
→ 起始手牌和第一个回合按对局配置继续

选将界面只能提交 general_id，不能直接修改 Player.general，也不能逐个把中文
技能名塞入角色状态。随机选将和 AI 选将必须调用与真人相同的提交接口。

当前没有实现身份，因此候选池不按主公技、身份或身份禁将进行筛选；以后加入
其他模式时，应由 GameMode/GeneralSelectionConfig 提供规则，不能改写通用
技能管理器。

9.3 稳定标识与数据文件

data/generals.yml 中每个技能引用统一写为：

skill_id: general.wusheng
name: 武圣

skill_id 是程序主键，发布后不得因显示文字调整而改变。武将技能统一使用
general.<稳定英文标识>；装备技能使用 weapon.*、armor.* 等命名空间。name
只用于选将界面、技能按钮和日志展示，不能作为规则分派条件。

同名技能若按规则确为同一个技能，应引用同一 skill_id；不同版本、旧版技能或
仅名称相同但规则身份不同的技能，必须使用不同 skill_id，并在版本配置中明确
选择。一个武将不得重复绑定同一 skill_id。

9.4 “技能描述.txt”的职责

“技能描述.txt”是面向玩家的规范文字和后续实现需求来源。以后增加武将时，
在该文件增加：

武将名称：
技能名称：官方技能效果

实际条目仍以项目要求的简洁格式为准，不附加实现说明、测试说明或程序字段。
技能描述应采用项目选定版本的官方牌面文字；若不同官方版本文字或效果不同，
先按本文件第十四章询问用户采用哪个版本。

程序不得在运行时解析中文自然语言并猜测技能效果。开发时读取“技能描述.txt”
后，必须完成三处明确衔接：

（1）在 generals.yml 用稳定 skill_id 将武将与技能绑定。
（2）在 SkillDefinition 注册技能类型、来源、时机、强制性等结构化信息。
（3）在统一技能处理器中实现效果并补充测试。

中文描述改变时，必须审查是纯措辞调整还是规则变化。纯措辞调整只更新显示
文本；规则变化必须同步修改 SkillDefinition、处理器和测试。禁止只改描述就
让旧代码静默冒充新效果。

9.5 技能获得、拥有、有效与失去

选将确认后，角色默认因其武将牌获得 General.skills 引用的技能。技能管理器
查询武将技能时，应同时满足：

（1）SkillDefinition.source_type == GENERAL。
（2）角色当前拥有相同 skill_id。
（3）角色及武将牌处于该技能允许的状态。
（4）没有覆盖该技能的失效效果。
（5）当前事件、时机、次数、目标和消耗合法。

以后出现获得、复制、授予、失去或恢复技能时，不得修改静态 General 数据。
应维护运行时 SkillGrant/SkillLoss 或等价来源记录，至少包含 skill_id、
source_id、granted_at_event_id、duration、invalidity_scope。一个技能可能有
多个来源；失去一个来源不一定等于失去该技能，必须在所有有效来源都不存在时
才视为不再拥有。

角色死亡后通常不再发动新的技能，但已经建立的技能事件和持续效果是否继续，
须依据技能文字、事件步骤和官方规则判断，不能统一粗暴撤销。

9.6 统一注册与事件接口

武将技能和装备技能共同进入 SkillManager，不为每名武将在 main.py、回合循环
或按钮回调里增加长期 if general.name == ... 分支。

每个武将技能至少声明：

skill_id、name、source_type=GENERAL、source_general_ids、kind、timings、
mandatory、controller_rule、cost、target_rule、usage_limit、effect_handler、
priority_group、invalidity_scope、description_key。

事件总线到达某一准确时机时：

收集当前拥有且有效的技能
→ 按时机与多角色结算原则排序
→ 锁定技直接建立技能结算
→ 含“可以”的技能建立可取消询问
→ 主动技只在合法空闲时间点列入 legal_actions
→ 确认时重新校验来源、消耗、目标和次数
→ 建立 SkillEvent 并执行处理器
→ 记录使用次数及结构化结果
→ 完成全部嵌套事件后返回父结算

UI 只读取技能管理器返回的 legal_actions 和 PromptContext。它可以展示技能名
与描述，但不能根据武将名或描述文字自行决定技能是否能发动。

9.7 未实现技能的处理

当前 generals.yml 可以提前保存以后计划实现的武将和技能引用，但“已出现在
候选数据中”不等于“技能已实现”。在正式开放某武将前必须执行完整性检查：

（1）每个 skill_id 都存在 SkillDefinition。
（2）每个需要改变状态的技能都有 effect_handler。
（3）所有声明 timing 均已接入事件总线。
（4）主动技存在合法动作生成与提交接口。
（5）可选技存在确定、取消、超时和 AI 路径。
（6）锁定技不产生可取消询问。
（7）最低测试集全部通过。

未通过检查的武将应标记为 unavailable/未实现，并从正式候选池排除；开发界面
可以展示，但必须明确标注“未实现”，不能让玩家选到没有实际效果的武将。

9.8 技能状态与次数标记

技能次数必须使用 skill_id 和明确作用域保存，例如：

(player_id, skill_id, phase_id)
(player_id, skill_id, turn_id)
(player_id, skill_id, round_id)
(player_id, skill_id, game_id)

不能把所有技能塞进 slash_used 一类专用布尔值。限定技、觉醒技、转换技阴阳
状态、蓄力值、武将牌上的牌或标记必须拥有结构化状态，并在正确生命周期清理。

9.9 结算中失去技能

一个事件开始结算后，应执行仍能执行的操作，跳过已无法执行的操作。技能在
结算途中失去不等于自动撤销已经建立且不再依赖该技能的持续效果；是否中止要
依据技能文字和当前结算步骤判断。

技能询问尚未确认时失去技能，提交时重新校验并拒绝过期选择。技能已经合法
发动并支付消耗后失去来源，已经建立的技能事件通常继续执行其仍能执行的部分；
若文字要求持续拥有、持续展示武将牌或持续装备某来源，则按该条件中止后续
操作。每一种特殊组合都应建立回归测试。

9.10 官方规则衔接原则

武将牌代表玩家操控的武将；角色可因武将牌拥有技能。技能的强制性、时机、
操作者和结算顺序以准确技能文字与规则定义为准。“锁定技”只说明必须发动或
产生效果，不赋予比一般技能更高的通用优先级。同一角色在同一时机拥有多个
可执行技能时，由其决定操作顺序；涉及多名角色时再按多角色结算原则处理。

实现具体武将前必须查阅项目选定版本的官方技能文字、规则集和勘误。不同版本
不可混用；无法确定时执行第十四章的询问流程。

9.11 技能代码模块化、按所选武将接入

项目预计会实现大量武将技能，因此具体技能效果不得持续堆积在 main.py、
GameUI、主回合循环或一个不断增长的 skills.py 中。主程序只负责通用游戏事件、
结算栈、合法动作提交、询问窗口、牌移动、动画、音频和界面绘制；每个技能的
专属条件、消耗、目标规则、事件处理器和 AI 评估应放在独立技能模块中。

推荐目录结构：

src/skills/
    registry.py                 技能定义索引与按 skill_id 解析
    base.py                     通用技能接口、上下文和结果类型
    general/
        guanyu/
            wusheng.py          general.wusheng 的专属规则处理器
        <其他武将>/
            <技能>.py
    equipment/
        weapon/
        armor/
    common/                     多个技能真正共用的规则组件

文件可以按单技能或同一武将的一组紧密相关技能组织，但不得形成包含所有武将的
巨大分派文件。只有确属通用规则的行为才能进入 common；不得为了减少文件数量
把多个无关技能合并成大量 if skill_id 分支。

接入流程必须为：

读取并校验 generals.yml
→ 玩家提交 general_id
→ 创建 Player 并取得 General.skills 中的稳定 skill_id
→ SkillRegistry 按这些 skill_id 解析对应 SkillDefinition 和 SkillHandler
→ 只把本局角色实际拥有的技能处理器挂入该局 SkillRuntime
→ 处理器按声明的 timings 订阅统一事件总线
→ 生成主动技能 legal_actions 和被动/触发技能候选
→ 游戏结束时释放本局订阅和临时技能状态

SkillRegistry 至少提供：

register(skill_id, definition, handler_factory)
resolve(skill_id)
build_runtime(players)
validate_general(general)

选择武将后“接入技能代码”指通过稳定 skill_id 建立处理器实例和事件订阅，
不是在选将按钮里 import 文件、执行中文文本或写 if general.name == ...。
registry 可以维护 skill_id 到模块路径的静态映射，并在 build_runtime 时按需
导入本局使用到的模块；也可以启动时加载轻量定义、选将后才实例化处理器。
无论采用哪种方式，技能局内状态都必须属于当前 GameSession/SkillRuntime，
不能保存在模块级全局变量里，以免多局游戏相互污染。

每个 SkillHandler 应使用统一接口表达能力，例如：

is_available(context)          转化后动作或技能在当前窗口是否合法
legal_costs(context)           返回可选择的实体牌、标记或其他消耗
legal_targets(context)         返回合法目标
on_event(event, context)       处理声明时机中的事件
resolve(skill_event, context)  执行已经确认并锁定参数的技能事件
ai_score(action, context)      只评估同一合法动作，不建立另一套 AI 规则

UI 不得直接调用 wusheng.py、某武将类或某个专属效果函数。UI 只能：

（1）绘制 SkillRuntime 返回的技能按钮状态。
（2）展示 legal_actions、PromptContext 和合法候选。
（3）把玩家选择提交给统一动作接口。
（4）消费结构化结算结果以播放动画、提示和音效。

技能专属模块不得直接修改界面控件、切换回合阶段或清空父结算。需要动画或提示
时返回结构化 VisualCue、AudioCue、LogEntry 或等价结果，由主程序统一表现。
需要继续父事件时返回 continuation/result，不得在技能模块中按牌名枚举南蛮、
决斗等父事件。

“技能描述.txt”仍只保存面向玩家的官方文字，不能把 Python 代码、模块路径或
实现参数写入其中，也不能在运行时把描述文本当代码执行。描述修改后由开发流程
更新对应技能模块、定义和测试；没有已注册处理器的技能不能因文字存在而开放。

新增一个武将技能时，标准改动范围应主要是：

（1）技能描述.txt 中增加或修改官方文字。
（2）generals.yml 中绑定稳定 skill_id。
（3）新增独立技能模块并在 registry 登记。
（4）补充该技能的规则测试、嵌套结算测试、取消/超时测试和 AI 同接口测试。

正常情况下不应修改 main.py。若新增技能迫使 main.py 增加专属牌名、武将名或
skill_id 分支，说明缺少通用事件、动作、选择、移动或表现接口；应先补通用接口，
再由技能模块接入。确实无法抽象且拿不准时，按第十四章流程询问用户。

10. 一般规则、牌规则、武器规则与武将技能冲突

冲突不能用“锁定技一定赢”解决。统一按以下步骤：

（1）先确定每条效果是否在当前事件、角色和时间范围内有效。
（2）再确定它们是否真的冲突，还是分别作用于合法性、目标、次数、伤害或
     牌的去向等不同层次。
（3）技能说明与基本牌/锦囊牌说明、游戏通则冲突时，遵循：
     技能说明 ＞ 基本牌/锦囊牌说明 ＞ 游戏通则或用语操作规范。
（4）武器技能和武将技能同属技能说明，不能仅凭来源或“锁定技”字样决定
     胜负；应按各自准确时机结算。
（5）同一角色在同一时机有多个可执行技能时，由该角色决定顺序；涉及多名
     角色时按多角色结算顺序逐个处理。
（6）明确的禁止条件应在合法性检查中生效；允许或追加次数的效果只修改它
     明确覆盖的限制，不能顺带解除其他禁止条件。
（7）后结算效果若改变了前一效果依赖的条件，继续前应重新检查剩余操作。
（8）实在存在文字冲突时，按当前采用版本的官方勘误和规则解释处理，并为
     该组合建立专门回归测试，不得把个案例外写成全局优先级。

规则引擎建议将修正分层：

VALIDITY（技能/装备是否有效）
→ PROHIBITION（是否禁止使用、响应或成为目标）
→ REPLACEMENT（是否替换原动作）
→ TARGET_AND_DISTANCE（目标、距离和范围）
→ COUNT_LIMIT（次数限制）
→ VALUE_MODIFIER（摸牌数、伤害值等）
→ RESULT_AND_DESTINATION（结果与牌的最终去向）

同层多个效果再按准确时机和角色选择顺序处理。每次修正应记录来源，便于日志
显示“哪条规则改变了什么”，不能只留下最终布尔值或最终数字。


六、防具效果的统一接口规范
==========================

1. 防具不能散落在各按钮函数中判断

防具至少需要以下统一入口：

（1）目标效果生效前：处理仁王盾、藤甲免疫等。
（2）需要响应时：处理防具提供的可选技能。
（3）伤害修正时：处理藤甲火焰增伤、白银狮子伤害上限。
（4）装备离区时：处理白银狮子回复。

2. 装备离区必须统一

所有装备离开装备区都必须经过 remove_equipment 或统一 CardMoveEvent，至少
覆盖：

（1）装备新防具替换旧防具。
（2）过河拆桥弃置装备。
（3）顺手牵羊获得装备。
（4）技能弃置或获得装备。
（5）死亡时清理装备。
（6）以后可能出现的交换、移动装备。

不能只在“过河拆桥”函数里特判白银狮子，否则替换和顺走会漏掉回复。

3. 无效与防止伤害不同

（1）“某牌对目标无效”：该目标不需要响应，也不进入该牌的目标效果。
（2）“防止伤害”：目标效果已经进行到伤害步骤，但伤害数值变为 0。
（3）日志、后续触发和统计必须区分这两种结果。


七、输入界面与引擎的职责
========================

1. 引擎负责

（1）规则条件和合法性。
（2）创建事件与保存结算上下文。
（3）决定当前允许哪些动作。
（4）改变游戏状态和移动卡牌。
（5）生成结构化日志或事件结果。

2. UI 负责

（1）根据当前事件显示按钮、卡牌和提示。
（2）把玩家选择提交给引擎。
（3）播放动画和展示判定结果。
（4）不能自己决定技能是否生效或直接扣血。

3. AI 负责

（1）从引擎提供的合法动作中选择。
（2）和真人使用相同的提交接口。
（3）AI 不得绕过响应窗口直接改状态。

4. 音效是规则事件的展示结果

（1）通常情况下，每次成功使用或打出一张牌、实际应用一次武器技能、实际发动一次武将技能，都应播放与该牌或技能对应的音效。
（2）音效只能在动作已经通过合法性检查并正式提交后播放。选择目标、弹出询问、取消发动、操作无效或结算被回滚时不得提前播放。
（3）“你可以……”类技能只在操作者确认发动后播放技能音效；操作者取消时不播放。
（4）锁定技无需询问，但只有在其触发条件满足且效果实际进入结算时才播放技能音效。仅检查条件而未生效时不播放。
（5）一个逻辑事件只能播放一次其主体音效。不得同时在“提交牌”和“开始结算”两个入口重复播放同一主体音效；嵌套结算中的响应牌、后续技能分别作为独立事件播放自己的音效。
（6）连续响应时，每张实际打出的响应牌各播放一次，但产生响应窗口的原牌只播放一次。例如反复要求响应的结算不得因重新打开响应窗口而重复播放原牌音效。
（7）武器技能、武将技能与卡牌效果发生嵌套时，应依据事件编号或结算上下文去重，不能依靠短时间静音来掩盖重复触发。
（8）音效播放失败、素材缺失或音频设备不可用时，只能跳过声音并记录可诊断信息，不得中断或改变游戏结算。
（9）规则引擎负责产生“出牌、打出、技能发动、伤害、回复”等结构化事件；UI 音频层订阅事件并选择素材。音频层不得反向修改规则状态。
（10）新增牌、武器和武将技能时，应同时登记其音效键；确无专属素材时允许使用明确的通用音效或暂时静默，但不得错误复用含义不同的语音。
（11）音效回归测试至少检查：成功动作播放一次、取消动作不播放、嵌套响应不重播父事件、同一结算不会因回调重入播放多次。
（12）背景音乐不属于规则事件音效，统一放在 sound/music 下并使用稳定英文ID。
      BGM必须通过独立音乐通道循环播放，不得占用卡牌、装备、技能或系统音效
      通道，也不得因任意规则音效播放而重启或中断。音频设备或BGM素材不可用
      时仅静默跳过，不得阻止游戏启动。

5. 按钮必须由当前提示类型解释

建议统一 Prompt 类型：

CHOOSE_ACTIVATE_SKILL
CHOOSE_RESPONSE_CARD
CHOOSE_TARGET
CHOOSE_CARDS
CHOOSE_OPTION
CONFIRM_ACTION

每个 Prompt 必须包含：

prompt_id
prompt_type
player
message
legal_actions
confirm_callback
cancel_callback
parent_event_id

收到点击时必须校验 prompt_id 仍是当前提示，防止动画结束后的旧点击影响新
结算。

6. 本人选择本人区域内的牌必须明牌操作

（1）操作者选择自己的手牌作为弃置、转化或技能代价时，必须直接在自己的手牌区点击选择；不得复用“查看或选择其他角色手牌”的背面牌面板。
（2）可选手牌应正常显示牌面并高亮；不可用于当前操作的手牌应置灰。再次点击已选牌应取消选择。
（3）规则允许选择本人装备区或判定区的牌时，应直接点击对应区域中的明牌；选中状态必须有清晰边框或高亮。
（4）确定按钮提交当前选择，取消按钮放弃本次可选操作。提交前必须校验选择数量、牌仍位于原区域且仍满足合法性。
（5）只有选择其他角色的未知手牌时才能显示牌背并进行盲选；不得把保密规则错误应用于本人手牌。
（6）同一次选牌提示中的视觉语义必须统一：当前可点击的牌保持正常亮度；
     当前不可点击、不能作为合法选择的牌必须灰暗处理。不能只靠文字提示区分。
（7）需要选择固定数量的牌时，在尚未选满规定数量以前，“确定”按钮必须为
     灰暗禁用状态；只有选择数量恰好满足要求并且所有选择仍合法时才能启用。
     点击禁用按钮不得推进结算，也不得用“点击后再报错”代替禁用状态。
（8）本人手牌被选中后必须向上提起；再次点击则落回原位并取消选择。多选时
     每一张已选手牌都必须保持上提，不能只抬起最后点击的一张。
（9）本人装备牌被选中后必须向右移动一段固定距离，并保留清晰的选中描边或
     高亮；取消选择后恢复原位。不可选装备保持原位并灰暗处理。
（10）上述规则适用于贯石斧、技能弃牌、转化牌、武将技能代价及以后所有
      “从本人区域选择若干张牌”的事件，不得为单张卡牌另造一套相反交互。
（11）点击装备本身发动装备技能后，即使该装备不是本次技能的材料牌，它仍是
      当前操作的发动来源，必须按“已选中装备”向右移动并高亮，不能因不在材料
      候选集合中而灰暗。例如进入【丈八蛇矛】选牌状态时，丈八蛇矛本身保持
      向右选中，手牌区另行显示可作为转化材料的牌。
（12）同一空闲时间点存在多个可主动操作的牌或技能入口时，新入口可以替换尚未
      确认的旧选择。替换必须是原子操作：先清除旧提示编号、旧材料选择、按钮
      回调和视觉选中状态，再建立新提示；不得执行旧提示的确认或取消结算，也
      不得让两套选牌状态同时存在。例如丈八蛇矛选牌过程中点击【武圣】，应直接
      由武圣选牌覆盖丈八选牌。
（13）技能文字要求使用“全部满足条件的牌”时，点击技能只进入固定材料确认态，
      不得立即发动。引擎在进入确认态时冻结当前合法材料ID：这些牌保持正常亮度
      并统一显示为已纳入操作，其他牌灰暗且不可点击；界面显示确定和取消按钮。
      点击确定后重新校验“全部”集合仍完全一致再提交，点击取消则只清除提示与
      视觉状态，不移动牌、不记录次数、不播放发动音效。AI可提交等价的无目标
      PlayerChoice，但不得绕过相同的合法性校验。

7. 牌移动事件与飞牌表现必须分层

飞牌不是根据“牌最后是否在弃牌堆”或“牌是否被展示”这一个条件猜测出来的。
规则引擎应先提交结构化的使用、打出、弃置、获得、判定、置入区域或其他牌移动
事件，表现层再根据事件的起点、终点、公开性和目标信息选择对应动画。

（1）使用或打出实体牌时，实体牌从真实来源区域离开并进入处理区或中央等待区；
     有目标的牌可同时显示从使用者到目标的指向，但指向不代替规则目标事件。
（2）因弃置进入弃牌堆的牌，按本规范第一章要求先正面进入中央等待区展示，
     再在该组结算允许时清除；动画原因必须记录为弃置，不能只因最终区域相同
     就与使用、打出或判定共用无法区分的无原因回调。
（3）展示不必然等于弃置，规则实体也不必然发生区域移动，但公开展示必须有
     与信息公开范围相符的视觉表现。若一张牌原本位于只对部分角色明牌的区域，
     规则要求“展示给所有角色”时，应建立独立 CardRevealEvent：规则实体继续
     留在原区域。由技能产生的纯展示牌统一进入与拆顺查看牌相同风格的独立
     展示框，全部正面列出并在规定时间后关闭，不进入中央等待区；牌或锦囊自身
     已有专用展示流程时使用该流程。展示内容只保存牌面快照、来源实体 card_id、
     来源区域、visibility、reason 和 source_event_id，不是新的 Card 实体，
     不得加入任何规则区域，也不得触发获得、失去、弃置或离区效果。展示框只
     消费 CardRevealEvent，不能决定技能效果、移动规则实体或承担规则推进。
（4）例如【火攻】目标展示一张手牌时，该实体牌仍在目标手牌区，目标本人仍可
     在手牌区看到它；同时创建公开展示副本，从目标手牌位置正面飞入中央等待区，
     供所有角色查看。后续弃置同花色牌、造成伤害或结束【火攻】结算时，只清除
     此展示副本。若展示牌后来因另一规则动作离开手牌区，应由新的牌移动事件
     处理实体牌，不得把清除展示副本当成实体牌移动。
（5）仅由特定角色观看牌堆顶、查看某角色手牌等非全体公开操作，应按 visibility
     限制展示对象，不得自动放入全体可见的中央等待区。判定等规则本来就要求
     实体牌进入处理区的公开事件，则移动并展示实体牌，不再额外制造公开副本。
（6）摸牌、获得、装备、置入判定区、置于牌堆顶或牌堆底等动作有各自明确的
     起点和终点，应播放与该区域移动相符的动画，不能一律飞到中央后消失。
（7）同一张实体牌的一次规则移动只能生成一组主体动画。多目标指向、展示停留
     和最终淡出可以是该组动画的阶段，但不得重复提交同一次牌移动。
（8）规则区域可以在动画开始前提交，但父结算是否恢复必须绑定同一事件编号
     和唯一完成回调。动画不得自行决定弃置、获得、扣除次数或推进阶段。
（9）表现层的动画请求至少应可追踪 card、from_zone、to_zone、reason、
     source_event_id、target_players 和 visibility；素材缺失只跳过表现，
     不能改变规则结果。
（10）一张已经向所有角色公开牌面的实体牌，在同一连续结算中被获得、转移或
      置入其他区域时，移动动画必须继续正面朝上；不能因为终点是其他角色的
      手牌区就临时翻回牌背。移动完成后，该牌在新手牌区中的日常显示再按手牌
      隐藏规则处理。CardMoveEvent 必须用 visibility 记录本次移动是否公开，
      表现层不得通过技能名称或获得者是否为AI猜测公开性。
（11）同一 DrawCardsEvent 或同一 CardMoveEvent 批次包含多张牌时，所有牌的
      主体移动动画必须使用同一开始时间并同时飞向各自终点；父结算应等待整批
      动画完成一次后恢复，不能逐张串行动画。一次获得多张牌同理，例如【奸雄】
      获得由【丈八蛇矛】转化【杀】的两张实体组成牌。牌的同时动画只反映同一
      规则批次，不得把两个先后发生的独立获得动作擅自合并。
（12）判定区是规则区域，不能因界面简化而删除 judgment_area 或改变延时锦囊
      的置入、无懈、判定、转移和离区流程。牌桌界面不再为每名角色绘制独立
      “判定区/空”面板，而在对应武将牌下沿横向显示延时锦囊判定标志；没有牌
      时不显示占位。所有座位共用“武将牌矩形→判定标志矩形”的布局接口，置入
      判定区、从判定区进入结算以及闪电传递的动画均使用同一标志中心，不能为
      1v1敌我座位各写一套判定区坐标。以后增加多人座位时只提供各座位武将牌
      矩形，不新增独立判定面板。

8. 牌、目标与按钮的可操作状态必须分层

“牌能否进入选择态”“某角色能否成为该牌的目标”“当前完整行动能否提交”
是三个不同问题，必须由独立的规则查询表示，不能用一个最终布尔值同时控制
手牌灰暗、武将灰暗和确定按钮。

（1）牌灰暗表示该实体牌在当前窗口不能进入选择态，例如动作类型不符、牌不在
     合法区域、当前时机禁止主动使用、次数限制已经达到，或牌自身的非目标条件
     不满足。灰暗牌不能通过点击进入选中状态。
（2）一张需要选择目标的牌当前没有任何合法目标，不代表该牌本身不能被选中。
     牌仍保持正常亮度并允许进入选牌态；选中后，由每名角色各自的目标合法性
     决定其武将区域是否灰暗。
（3）目标灰暗表示该角色不能成为当前所选牌或技能的目标，例如距离或攻击范围
     不符、禁止成为目标、目标已死亡、区域条件不满足、延时锦囊重名，或目标
     数量与既有选择冲突。点击灰暗目标不得写入目标集合。
（4）不能因为某一名目标非法就把牌置灰，也不能因为存在另一名合法目标就让
     当前非法目标可点击。目标合法性必须逐个角色计算。
（5）确定按钮只在完整操作达到可提交状态时启用，包括牌仍在合法区域、消耗
     有效、目标数量正确、全部已选目标合法，以及当前事件和次数限制仍然有效。
     尚未选择必需目标时，牌可以已选中，但确定按钮必须灰暗且不可点击。
（6）取消按钮是否启用取决于当前是否存在可取消的选择或询问；禁用按钮必须
     拒绝点击，不能先执行回调再由业务逻辑撤销。
（7）规则引擎应提供等价于 can_select_card、is_legal_target 和
     can_submit_action 的分层接口；UI 只消费这些结果，不得按牌名自行推测距离、
     区域或目标条件。
（8）本规则适用于所有需要目标的基本牌、普通锦囊、延时锦囊、装备技能、
     武将技能和转化牌。不得只为某张牌增加“无目标仍可选”或“超距离目标灰暗”
     的界面特例。


八、测试规范
============

每个新卡牌或技能至少测试：

1. 条件满足并发动/生效。
2. 条件不满足时不发动/不生效。
3. 可选技能点击确定。
4. 可选技能点击取消。
5. 可选技能超时按取消处理。
6. AI 与真人走相同规则接口。
7. 目标在结算中死亡或失效。
8. 嵌套濒死后能返回父事件。
9. 多目标队列不会被一个目标的响应清空。
10. 动画回调不会重复推进阶段。
11. 卡牌最终区域正确。
12. 日志与实际状态一致。

回合阶段必须至少测试：

（1）六阶段顺序正确。
（2）跳过判定、摸牌、出牌阶段后仍进入正确下一阶段。
（3）准备阶段和结束阶段的技能询问全部完成后才推进。
（4）旧定时器和旧动画回调不能重复推进。
（5）当前角色死亡时能安全转到下一名存活角色。

测试执行采用分层回归，不要求每次修改都从第一个武将开始运行全部武将流程：

（1）开发中的普通武将技能修改，先运行该武将自己的定向测试文件。
（2）若修改复用了某个公共窗口，再补跑该窗口所属的子系统测试，例如判定、
     无懈、伤害、牌移动、转化牌、装备或AI策略测试；不重复运行无关武将。
（3）只有修改 GameEngine、SkillRuntime、事件模型、伤害/判定/响应栈、通用
     牌移动等会影响大量武将的公共底层，或准备打包、发布版本时，才运行完整
     测试集。
（4）出现线上或实际对局回归错误时，为该错误建立最小定向测试并加入对应武将
     或子系统文件；以后由该小测试守住边界，不依赖每次人工重跑全部流程。
（5）定向测试通过只能证明本次影响范围内的行为；发布前完整测试仍是最终门禁，
     不得因为日常开发采用分层测试而永久取消。


九、后续修改前检查清单
======================

编写代码前逐项回答：

1. 这是使用、打出、弃置、失去、获得、伤害还是失去体力？
2. 它发生在回合、阶段或事件的哪个精确时机？
3. 这是锁定技还是含“可以”的可选技能？
4. 若可选，确定和取消分别返回到哪里？
5. 它会插入哪个父事件？需要保存哪些上下文？
6. 应使用栈还是队列？
7. 多目标时只影响当前目标还是整张牌？
8. 是否会触发判定、改判、无懈、伤害、濒死或死亡？
9. 卡牌从哪个区域移动到哪个区域，移动原因是什么？
10. 玩家、AI、超时三种输入是否走同一规则接口？
11. 动画只是展示，还是被错误地承担了规则推进？
12. 是否补充了确定、取消、嵌套恢复和区域移动测试？

如果这些问题没有答案，不应直接在 main.py 的按钮回调中添加临时 if 分支。


十、当前项目应遵循的重构方向
============================

1. Phase 应补全 PREPARE，使回合成为标准六阶段。
2. 当前 response_queue 可继续用于同层多目标，但嵌套上下文应逐步改为明确的
   ResolutionFrame/事件栈。
3. 当前 dying_stack 的“保存并恢复父响应”思路应推广到判定、改判、无懈链
   和其他可选技能。
4. DamageEvent 应继续作为统一伤害入口，不在各卡牌函数里直接扣体力。
5. 装备离区应继续统一，不允许新增绕过白银狮子离区触发的删除路径。
6. 每次重构只改变一类职责，并用自动测试保护已有南蛮、万箭、决斗、无懈、
   濒死、连环和装备逻辑。

十三、牌堆构筑与检索规范
========================

1. 当前采用的牌堆版本

本项目当前使用“不含【木牛流马】的军争牌堆”，共 160 张实体牌。构成以
data/cards.yml 为唯一程序数据源，本节记录的是该文件当前应保持的基线。

总数校验：

基本牌 85 张
锦囊牌 50 张
装备牌 25 张
合计 160 张

花色校验：

黑桃 40 张
红桃 40 张
梅花 40 张
方块 40 张

装备槽位校验：

武器 12 张
防具 6 张
-1 坐骑 3 张
+1 坐骑 4 张
宝物 0 张

【木牛流马】不得出现在当前牌堆。若以后切换扩展版本，应新建明确的
deck_profile，不能静默修改本基线。

2. 实体牌与唯一身份

每张牌是独立 Card 实体，至少包含：

id：全局唯一，不因移动区域而改变
name：牌名
suit：spade、heart、club、diamond
rank：A、2—10、J、Q、K
kind：basic、trick、equipment
equipment_type：仅装备牌使用

同名、同花色、同点数的两张牌仍必须拥有不同 id。移动、获得、弃置、判定和
动画均按实体牌 id 追踪，不能只按牌名删除，否则会删除错误副本。

3. 牌堆与弃牌堆的数据结构

当前引擎使用：

draw_pile: list[Card]
discard_pile: list[Card]
processing_area: list[Card]

约定：

（1）draw_pile 列表末尾是牌堆顶，摸牌使用 pop()。
（2）draw_pile[0] 是牌堆底。
（3）弃置使用 discard_pile.append(card)。
（4）弃牌堆通常只需要保存实体牌集合和加入顺序；任何规则若需要查看弃牌堆
     顶或具体顺序，再按“列表末尾为最新进入弃牌堆的牌”解释。
（5）处理区中的牌不属于牌堆或弃牌堆，不能同时存在于两个列表。
（6）同一实体牌在任意时刻只能处于一个区域。

禁止把牌堆改为 set。set 会丢失顺序，也不能表示多张属性相同但 id 不同的牌。
若为检索性能建立索引，索引只能引用 draw_pile 中的实体牌，不能代替牌堆本身。

4. 初始化洗牌

加载 data/cards.yml 后：

（1）验证每张牌 id 唯一。
（2）验证总数、类别数、花色数和装备槽位数符合 deck_profile。
（3）复制实体牌列表到 draw_pile。
（4）调用 random.shuffle(draw_pile) 做一次均匀随机洗牌。
（5）discard_pile 和 processing_area 初始化为空。

测试必须允许注入固定随机种子或直接设置牌堆顺序。正式对局默认使用系统随机
状态，不在每次摸牌前重复洗牌。

5. 牌堆耗尽与重洗

需要操作牌堆顶而 draw_pile 为空时：

（1）若 discard_pile 非空，将弃牌堆中的全部牌作为重洗候选。
（2）先清空 discard_pile。
（3）对候选牌调用 random.shuffle。
（4）将随机顺序结果作为新的 draw_pile。
（5）继续原本被暂停的摸牌、判定或翻牌动作。

重洗时不得包含：

角色手牌、装备区、判定区、处理区、武将牌上的牌、临时展示但尚未完成移动的牌。

若 draw_pile 和 discard_pile 均为空，应由调用者得到明确的“无牌可操作”结果，
不能凭空生成牌，也不能无限递归重洗。

不得在弃牌堆刚出现第一张牌时自动重洗。只有规则动作确实需要操作牌堆且牌堆
为空时才重洗。

6. 从牌堆顶摸牌、观看与展示

（1）摸 N 张：调用统一 draw_to_hand(player, N, reason) 建立一个
     DrawCardsEvent；底层仍逐张从列表末尾弹出，但不得分别建立 N 次摸牌。
     draw_cards(N) 只允许作为牌堆底层取牌原语，用于判定、亮出牌堆顶牌、
     初始发牌等不属于规则术语“摸牌”的动作，不能直接给角色增加手牌。
（2）观看牌堆顶 N 张：读取 draw_pile[-N:] 的顶端顺序副本，不移动实体牌；
     返回顺序必须明确“第一张牌堆顶牌”。
（3）展示牌堆顶牌：先按规则移动到处理区或展示区，结算后再确定最终去向。
（4）将牌置于牌堆顶：按希望随后弹出的逆序 append。
（5）将牌置于牌堆底：插入索引 0；多张牌必须明确其上下顺序。
（6）任何观看操作都不得意外 shuffle 或改变未被选择牌的相对顺序。

7. 从牌堆定向检索某种牌

所有“从牌堆中寻找/获得/使用一张符合条件的牌”必须调用统一接口，例如：

search_draw_pile(
    predicate,
    selection="first_from_top" 或 "random" 或 "controller_choice",
    remove=True/False,
    reveal=True/False,
    shuffle_after=False
)

predicate 可按牌名、类别、花色、颜色、点数或装备类型组合，禁止在业务代码里
复制多套检索循环。

默认规则：

（1）定向检索只搜索当前 draw_pile，不把弃牌堆、手牌区或处理区混入候选。
（2）“从牌堆顶开始寻找”从列表末尾向索引 0 扫描，找到第一张即停止。
（3）“随机获得一张符合条件的牌”先收集候选实体，再随机选择一个。
（4）“选择一张符合条件的牌”先建立候选快照，再由 controller 选择。
（5）remove=True 时，从 draw_pile 删除准确实体牌，再移动到指定区域。
（6）未命中的牌保持原相对顺序，除非牌或技能文字明确要求洗牌。
（7）只有文字明确要求“然后洗牌”时，才在检索后 shuffle。
（8）找不到符合条件的牌时返回 None 或空列表，执行父效果中仍能执行的部分。
（9）检索结果公开与否由规则文字决定；UI 不得因调试方便泄露整个候选集合。
（10）提交选择时重新验证所选牌仍在 draw_pile，避免嵌套事件造成过期选择。

定向检索不是摸牌。检索得到的牌应记录移动原因，例如 SEARCH_GAIN、
SEARCH_USE、SEARCH_EQUIP，不能错误触发只与“摸牌”有关的技能。

8. 牌堆索引规划

160 张牌使用 list 顺序扫描性能足够。只有出现大量模拟或更大扩展牌堆时才考虑
维护辅助索引：

by_name: dict[str, set[card_id]]
by_suit: dict[str, set[card_id]]
by_kind: dict[CardKind, set[card_id]]
by_equipment_type: dict[str, set[card_id]]

辅助索引必须在每次牌移动时同步更新，并且最终仍以 draw_pile 中是否存在该
card_id 为准。索引不能决定牌堆顶顺序；“从顶开始找”仍必须扫描 draw_pile。

十四、不确定时询问用户的编程规范
==============================

1. 基本原则

本规范、当前代码、自动测试和官方规则资料用于帮助作出可靠实现，但不能假定
所有产品选择都有唯一答案。

如果完成查证后仍存在会明显改变规则、交互、数据结构、兼容性或工作范围的
不确定性，不得擅自选择一个影响重大的方向，应暂停相关修改并询问用户。

询问不是把所有判断推回给用户。开发者应先完成可以安全完成的调查和分析，
把问题缩小为少数明确选项，再请求用户决定真正属于产品意图的部分。

2. 询问前必须完成的调查

提出问题前，依次检查：

（1）本文件是否已有明确规范。
（2）data/cards.yml、现有模型、引擎和 UI 实际如何表示相关状态。
（3）自动测试是否已经表达预期行为。
（4）项目中的 README、CONTEXT、说明文件或历史实现是否给出约定。
（5）官方卡牌文字、官方规则集、勘误和当前采用版本是否能够解决问题。
（6）是否可以通过只读检查、最小复现实验或新增测试确定现状。
（7）不确定的是“规则事实”“程序实现方法”还是“用户偏好/产品选择”。

能通过上述方式可靠查明的事实，不应反复询问用户。实现方法有明显最佳实践且
不会改变用户体验时，应按规范自行完成并说明。

3. 必须询问用户的情况

出现下列任一情况，且调查后仍无法消除分歧时，应询问：

（1）不同官方版本、不同模式或不同勘误给出不同规则，而项目未声明采用哪版。
（2）用户需求与官方规则、现有规范或已经实现的行为相互冲突，无法同时满足。
（3）两种实现都会改变玩家可执行操作、按钮语义、信息公开程度或结算顺序。
（4）需要决定采用完整官方规则还是项目简化规则。
（5）需要删除、迁移或重置存档、配置、牌堆数据或其他难以恢复的数据。
（6）需要进行大规模架构替换，而小范围兼容改造和彻底重构的成本、风险差异
     很大。
（7）无法判断某项效果是当前任务范围，还是用户希望以后再实现。
（8）卡牌或技能文字本身存在歧义，官方资料也没有足够明确的解释。
（9）多个合法目标、技能或效果的默认 AI 策略会显著影响游戏体验，而用户没有
     给出偏好。
（10）当前缺少实现所必需的素材、数据、规则版本或关键上下文。
（11）继续实现必须获得新的权限、外部协调或扩大任务范围。
（12）任何合理假设都有较高概率导致用户之后要求推翻已经完成的大量代码。

4. 通常不需要询问的情况

下列情况应自行处理：

（1）变量命名、函数拆分、测试组织和等价重构等内部实现细节。
（2）可以从 cards.yml、代码、测试或官方规则直接确定的事实。
（3）修复明显的语法错误、重复回调、数据泄漏、越界或牌区重复等程序错误。
（4）增加不改变规则行为的日志、类型标注、断言和回归测试。
（5）采用本规范已经明确要求的结算栈、队列、PromptContext、JudgmentEvent
     或统一牌移动接口。
（6）存在安全、可逆、与用户目标一致的默认实现，且之后修改成本很低。

不能因为工作量较大或实现复杂就询问用户替开发者作技术判断。

5. 询问问题的标准格式

每次询问应尽量只围绕一个真正阻塞决策，并包含：

背景：
用一至三句话说明当前正在实现什么。

已确认事实：
列出从代码、数据或官方规则中查到的关键证据。

不确定点：
明确指出只有哪一项产品意图无法从现有资料确定。

可选方案：
通常提供二至三个互斥方案。每个方案说明：

（1）玩家看到的行为。
（2）与官方规则的关系。
（3）对现有代码和存档的影响。
（4）主要优点、缺点和实现风险。

推荐方案：
给出开发者认为最合理的默认选择和具体理由。不能只说“都可以”。

需要用户回答：
要求用户选择方案，或回答一个足以解除阻塞的简短问题。

示例结构：

“我确认当前项目采用160张军争牌堆，代码中没有宝物槽。现在新增的牌在不同
版本中分别作为宝物或普通装备，这会影响装备区结构。

方案A：按当前官方版本增加宝物槽，规则更完整，但需要迁移装备区和UI。
方案B：暂按普通装备简化，改动较小，但与官方版本不完全一致。

我推荐方案A，因为项目规范要求优先遵循当前官方牌面。你希望采用A还是B？”

6. 询问时禁止的做法

（1）只问“怎么办”“要不要改”而不说明具体分歧。
（2）给出大量相似选项，让用户替开发者设计全部技术方案。
（3）隐瞒推荐方案或关键风险。
（4）在用户回答前先完成会锁死其中一个方案的大量修改。
（5）把能够从项目文件或官方规则查到的问题交给用户回忆。
（6）连续提出多个互相依赖的问题；应先问最上游、最能缩小后续选择的问题。
（7）用户已经明确回答后，以相同理由重复询问。

7. 等待回答期间可以继续的工作

询问阻塞的是某个具体分支，不代表所有工作都必须停止。等待用户回答时，可以
继续：

（1）完成与该选择无关的只读调查。
（2）补充能够覆盖双方共同要求的测试。
（3）整理接口、类型和事件上下文，但不提交偏向某方案的行为。
（4）记录两个方案共同需要的数据。
（5）明确列出收到回答后将修改的文件和测试。

不得继续会造成数据丢失、规则行为改变或大量返工的分支。

8. 收到用户回答后的处理

（1）先用一句话复述最终选择，确保没有误解。
（2）将选择写入适当的项目规范、配置、测试或注释，避免以后再次产生同一歧义。
（3）按选择继续实现，不重复询问已经决定的问题。
（4）如果用户答案同时引入新的重大冲突，应指出新的具体冲突并再次按本流程
     询问，而不是静默猜测。
（5）完成后说明最终行为、验证结果，以及该选择记录在何处。

9. 默认假设的使用边界

如果不确定性较小、不改变产品方向且实现可逆，可以采用默认假设继续，但必须：

（1）选择最符合本规范和官方规则的方案。
（2）在工作说明中明确写出假设。
（3）把假设集中在接口或配置中，避免散落成难以修改的分支。
（4）用测试记录当前行为。

如果假设会导致规则版本、玩家选择权、隐藏信息、数据结构或大范围代码不同，
则不属于“小假设”，必须询问用户。


十五、武将技能模块与DIY武将工作流
================================

1. 技能文件的统一位置

所有武将技能的规则实现统一放在：

src/skill_modules/general/<general_id>/<skill_key>.py

其中：

（1）general_id 使用 data/generals.yml 中武将的稳定 id，只使用小写英文、
     数字和下划线。
（2）skill_key 使用技能的稳定英文或拼音键，只使用小写英文、数字和下划线。
（3）每一级目录必须包含 __init__.py。
（4）例如：

src/skill_modules/general/guanyu/wusheng.py
src/skill_modules/general/caocao/jianxiong.py
src/skill_modules/general/diy_general/new_skill.py

武将目录表示“该技能代码最初归档在哪里”，不表示只有这个武将能够拥有该技能。
技能归属由武将数据引用的 skill_id 决定，不由文件夹路径、文件名或显示名称决定。

2. 已有技能的复用

DIY武将要拥有已经实现的技能时，不复制技能文件，不创建同名处理器，也不重新
注册技能。只在 data/generals.yml 的该武将 skills 中引用现有稳定 skill_id。

例如，一个DIY武将同时拥有【武圣】和【奸雄】，应引用：

general.wusheng
general.jianxiong

复制 wusheng.py 或 jianxiong.py 不会自动赋予技能，反而可能造成重复 skill_id、
重复注册和两份规则逐渐不一致。

3. 新技能的稳定ID

标准或项目中已经存在的技能沿用已注册的 ID，例如 general.wusheng。

全新的DIY技能默认使用：

general.<general_id>.<skill_key>

例如：

general.diy_general.new_skill

skill_id 是程序主键，技能中文名只负责显示。不同规则不得共用同一 skill_id；
同一规则也不得因多个武将拥有而复制出多个 skill_id。

若DIY技能与标准技能同名但文字或效果不同，必须建立新的DIY skill_id，不能
静默覆盖标准技能实现。

4. 单个技能模块应包含的内容

每个新技能 py 文件至少负责：

（1）唯一 SkillDefinition。
（2）技能的时机、类型、是否锁定或可选。
（3）候选牌、候选目标和发动条件。
（4）提交时的再次合法性校验。
（5）规则结算及其 CardMoveEvent、DamageEvent、JudgmentEvent 等事件结果。
（6）技能需要的模块化处理器，例如触发技处理器或牌转化处理器。

技能模块不得直接：

（1）绘制按钮或牌面。
（2）访问 pygame 控件。
（3）写 main.py 专属状态。
（4）直接播放音效或启动动画。
（5）按武将中文名判断技能是否存在。

界面只消费通用 PromptContext、技能结算结果、牌移动事件和表现事件。

5. 注册与武将绑定

创建新技能文件后，必须完成：

（1）在 src/skill_modules/registry.py 中显式导入技能定义和处理器。
（2）按技能类型加入对应注册表，例如 GENERAL_SKILL_DEFINITIONS、
     TRIGGERED_SKILL_HANDLERS 或 CONVERSION_SKILL_HANDLERS。
（3）在 data/generals.yml 中通过 skill_id 绑定到武将。
（4）由 loader 校验 playable 武将引用的全部 skill_id 已注册。

当前项目不依靠扫描文件夹自动发现技能。单纯创建或复制 py 文件不等于技能已经
接入游戏。

6. main、engine 与 skills 的边界

main.py 只能处理通用询问、选择、动画、音效和结算恢复，不能出现某个武将技能
名称或 skill_id 的专属 if/elif。

src/engine.py 只能提供通用规则入口，例如伤害、牌移动、判定、牌转化提交和目标
合法性，不为单个武将技能建立专用分支。

src/skills.py 负责注册表查询和通用分派。具体技能的牌色、数量、触发条件和效果
必须留在对应技能模块中。

如果新增技能需要一个当前不存在的时机或事件，应先扩展通用 SkillTiming、事件
模型和分派接口，再由技能模块使用；不得把技能规则倒灌进 main.py。

7. 武将皮肤语音的统一位置

武将技能与阵亡语音统一按 general_id、skin_id 整理：

sound/general/<general_id>/<skin_id>/skill/<skill_id>/1.ogg
sound/general/<general_id>/<skin_id>/skill/<skill_id>/2.ogg
sound/general/<general_id>/<skin_id>/death.ogg

有更多技能语音时继续使用 3.ogg、4.ogg。general_id、skin_id、skill_id 均必须
使用稳定内部标识，不得使用可能修改的中文显示名称作为程序路由依据。

现有武将牌图片、技能语音和阵亡语音均归入 default 皮肤。General 的
default_skin_id 与 Player 的 skin_id 默认都为 default；开局选将尚未进入独立
皮肤选择时必须展示 default 皮肤，不得随机展示或继承上局选择。

新式皮肤武将牌图片统一放在：

images/generals/<general_id>/<skin_id>/card.png
images/generals/<general_id>/<skin_id>/card.jpg

同一皮肤只保留其中一种受支持格式。现有 images/generals 下按武将中文名平铺的
旧图片视为 default 兼容素材；新接入图片必须使用 general_id/skin_id 目录。
图片显示时保持原始比例并居中裁切到武将牌区域，不得直接拉伸人物。

武将皮肤原画与武将牌边框必须分层保存和绘制。新接入武将的
use_portrait_frame 默认开启；界面无论使用哪个 skin_id，都先绘制原画，再按
稳定 general_id 叠加 images/general_frames/runtime/<general_id>.png。
同一武将的所有皮肤共用该边框，不得把边框重复烘焙进每张皮肤。旧武将可在
General 数据中显式关闭该功能；当前关羽、曹操关闭并保留原牌面。该差异只能由
通用数据字段表达，不得在 main.py 中按武将名建立 if/elif 特例。

势力字和武将姓名属于专用边框美术的一部分，不由界面运行时额外绘制文字。
势力字位于边框左上侧，姓名使用与势力字一致的书法风格，在势力字下方的左侧
竖槽中逐字排列。启用专用边框的武将，底部黄色手牌信息只显示
“当前手牌数/当前手牌上限”，不得重复姓名。敌方武将的该数字放在牌面左侧
竖排姓名下方，不再占用底部横栏；关羽、曹操等原画已经包含姓名的旧武将也只
额外显示数字，不得在黄色文字中重复姓名。本地武将可保留底部数字位置。
敌我武将牌和选将界面必须读取同一个字段与同一边框资源；悬停说明框仍可完整
显示武将姓名及公开资料。

敌方的武器、防具、进攻马和防御马展示栏仍属于武将牌内部布局，但必须整体
放在牌面右下区域：左侧避开势力、姓名及侧面机械装饰，右侧紧邻但不得覆盖体力
勾玉列，底部与武将牌内侧边框保留统一的小间距，形成视觉上的内侧贴合。
阶段图标和决策读条继续使用武将牌下方原位置，不得因装备栏调整而挪到牌面左侧
或其他未经规定的位置。

敌方黄色手牌数字必须对准左侧姓名栏的水平中心，并紧接在姓名末字下方。专用
透明边框的窄姓名槽和关羽、曹操等旧原画姓名栏可以使用不同布局参数，但必须
通过“边框类型对应布局”统一计算，不得按武将中文名写位置特例。

选将界面的底部公开信息栏不属于手牌信息。无论武将是否启用专用边框，都必须
统一显示“势力·武将名  体力N”，下一行统一显示技能名；不得因启用边框而把
其中某张牌改成“体力上限N”等不同格式。

技能语音通过 general_id＋skin_id＋skill_id 查找，阵亡语音通过
general_id＋skin_id 查找。当前皮肤缺少某类语音时回退同一武将的 default
皮肤；default 仍缺失时静默跳过，不得使用其他武将或其他技能的语音冒充。

音效只能在技能已经合法提交并实际进入结算后播放。点击技能、选择材料、取消、
超时、目标非法或提交失败均不得播放技能发动语音。

整理音效时优先检索 assets 中已有素材，确认素材确实对应技能后再复制到 sound
的统一位置，并验证每个 ogg 能被音频系统加载。找不到或无法确认素材时，不得用
无关语音冒充；应按第十四节说明缺失内容并询问用户。

8. 《技能描述.txt》作为DIY需求入口

用户以后可以直接修改 docs 目录的《技能描述.txt》，用技能文字表达要新增、
复用或修改的武将技能。收到“依据技能描述实现DIY武将”等要求后，开发者应主动
读取该文件的完整内容，并以其中新增或修改的条目作为本次需求输入。

推荐格式：

武将名：
【技能名】：完整技能文字。

若是全新武将，建议同时写明武将ID、势力和体力，例如：

武将名：自定义武将
武将ID：diy_general
势力：魏
体力：4
【新技能】：完整技能文字。

技能文字中的“可以”“锁定技”“使用”“打出”“弃置”“获得”“展示”“伤害”
“失去体力”和各结算时机必须按本规范的严格术语解释。

《技能描述.txt》是实现需求来源，不是运行时脚本。修改文字后，开发者仍须完成
技能模块、注册表、武将数据、通用接口、音效整理和自动测试，不能让 main.py
读取中文描述后临时解释执行。

9. 依据技能描述自动实施时的职责

当用户要求依据《技能描述.txt》实现技能时，开发者应自行完成：

（1）比较文件变化并识别新增、复用、修改或删除的技能需求。
（2）优先复用规则文字相同且已经实现的稳定 skill_id。
（3）为全新或规则不同的技能建立唯一 skill_id 和模块目录。
（4）确定精确触发时机、父事件、可选/强制属性、候选与取消恢复点。
（5）补充所需的通用事件或接口，但不在 main.py、engine.py 建技能特例。
（6）在 generals.yml 中完成绑定，并保持不可用的半成品武将不进入 playable
     选择池。
（7）从 assets 整理对应音效到 sound，接入稳定 skill_id，并遵守实际发动后
     才播放的原则。
（8）补充确定、取消、AI、超时、非法提交、区域移动、嵌套恢复和音频资源测试。
（9）运行完整测试，并说明最终实现的技能、文件位置、音效来源和验证结果。

开发者不应要求用户重复说明能从技能文字、现有代码、官方规则或 assets 中查明
的内容。

10. 需要询问的DIY信息

若技能文字存在会改变玩家选择权、隐藏信息、目标范围、结算顺序或规则版本的
歧义，应按第十四节完成调查后询问用户，不能自行补写关键规则。

全新武将若缺少势力、体力或其他开局必需数据，可以先完成不依赖这些数据的技能
调查与接口整理，但在将其设为 playable 前必须询问并补齐。

若用户只是把已有技能组合给DIY武将，且文字与现有实现一致，应直接复用，不因
武将不同而重新询问或复制代码。

11. 新技能完成检查清单

每个DIY技能完成前必须确认：

（1）技能文件位于约定模块目录。
（2）skill_id 唯一且已经注册。
（3）武将只通过 skill_id 引用技能。
（4）main.py、engine.py 和 src/skills.py 没有该技能名称或 ID 的特例。
（5）使用与打出、牌与目标、规则状态与动画状态已经分离。
（6）可选技能的确定、取消、AI和超时路径完整。
（7）实体牌区域移动可审计，不复制或丢失规则实体。
（8）技能音效只在实际发动后播放，素材已整理并可加载。
（9）已有技能复用时没有复制实现文件。
（10）专项测试与完整回归测试全部通过。

12. 武将技能的AI策略位置与接口

武将技能的AI使用策略必须与技能规则实现放在同一个技能模块中，即：

src/skill_modules/general/<general_id>/<skill_key>.py

技能处理器可以按技能类型提供以下策略方法：

（1）ai_should_activate：判断可选触发技是否发动。
（2）ai_choose_cards：从规则层给出的合法候选牌中选择材料或代价。
（3）ai_choose_target：从规则层给出的合法目标中选择目标。
（4）以后出现多模式、多选项或发动顺序时，应增加通用的策略结果类型，不得在
     main.py 中按技能名称补写分支。

AI策略只负责在合法集合中作选择，不能自行放宽技能条件、伪造候选牌或绕过提交
校验。真人与AI必须共用同一个技能定义、候选生成、目标合法性和最终提交校验；
二者的区别仅是由界面输入还是策略方法生成选择。

src/skills.py 只负责根据注册表找到技能处理器、构造 SkillAIContext、调用策略
并复核策略结果。main.py 只负责AI行动的定时、通用提示提交、动画和结算恢复，
不得出现某个武将技能名称或 skill_id 的AI特例。

可选触发技没有实现AI策略时，AI默认不发动；锁定技和其他强制效果不得由AI选择
取消。牌转化技能的AI策略必须同时考虑材料保留价值和当前合法目标，不能因为
当前没有合法目标就改变该牌本身能否被选择的规则状态。

新增或修改武将技能时，必须同时检查以下AI路径：

（1）主动发动、响应发动和受到事件后触发是否分别有正确上下文。
（2）确定、取消、无合法材料、无合法目标和结算前状态变化能否安全恢复。
（3）AI策略返回的牌和目标是否再次经过与真人相同的规则校验。
（4）main.py、engine.py 和 src/skills.py 是否仍然没有该技能的专属AI分支。

AI对普通牌、装备和公共代价的估值应放在独立的通用策略层，不能让弃牌阶段、
丈八蛇矛、武圣、贯石斧等分别维护互相矛盾的“低价值牌”表。统一估值至少允许
读取当前体力、手牌上限、已有装备、牌的即时合法用途、有效目标和响应保留价值；
具体技能仍可在自己的模块中增加局部约束，但应复用通用估值作为基础。

AI出牌阶段的“牌类总优先级”必须与“某一类牌内部如何选择牌、目标和是否放弃”
分离。总优先级应由一个稳定的类别调度入口统一排列；每个类别只实现自己的策略，
并继续调用真人共用的规则、动画和结算接口。调整优先级时不得复制牌的结算流程，
不得在多处维护互相冲突的顺序，也不得把策略顺序误写成牌或目标的合法性条件。
AI每完成一个动作后必须重新读取当前局面，再从最高优先级类别开始判断。

装备牌的“是否装备”应作为独立策略域，不与“装备已经生效后是否发动技能”
混为一项。装备决策至少考虑空槽或替换、旧装备损失、装备后攻击范围、当前可用
牌、目标防具、铁索传播、手牌上限和动作后的剩余手牌价值。手牌未超过上限且
没有明确战术升级时，不应为减少一张手牌而替换同槽等效装备。

AI可以进行只读的轻量预推演，但不得为了评分临时修改真实Player、装备区、牌区、
阶段标记或结算栈，也不得调用会产生日志、移动牌或触发技能的结算函数后再回滚。
轻量推演应通过显式候选参数计算“假如装备/转化后的范围、有效牌面和收益”，
最终动作仍须经过真人共用的提交校验。完整搜索深度、未知信息模型和对手响应概率
属于更高层策略能力，可以以后替换评分器，但不能改变规则层接口。

防具会令某个【杀】无效，通常只是AI不应提交该牌与目标组合的策略结论，不是牌
不能选中或目标在规则上非法。策略层可以过滤明显无收益的组合；规则层仍应保持
牌选择、目标合法性与最终提交校验三者的原有边界。

13. 有效牌面与实体组成牌必须分离

转化牌、复合牌和被修改属性的牌必须同时保存两类信息：

（1）有效牌面：结算时被视为什么牌，供牌名、属性、伤害性质、响应要求和牌效果
     判断使用。DamageEvent 中使用 source_card 表示。
（2）实体组成牌：实际从手牌区或装备区提交、进入处理区并最终被移动的原始牌。
     DamageEvent 中使用 source_physical_cards 表示，且允许包含多张牌。

有效牌面可以是虚拟副本，不属于任何规则区域，不得被获得、弃置、移动或重复
加入牌堆。任何“获得造成伤害的牌”“将此牌置于……”等涉及区域移动的效果，
必须操作全部仍在合法区域中的实体组成牌，不能拿虚拟有效牌去处理区做对象
身份判断。

转化牌作为“使用牌”提交时，其全部实体组成牌必须从原区域进入处理区，并一直
保留到该次使用、伤害、濒死和“受到伤害后”等嵌套结算结束；之后只有仍留在
处理区的实体牌才能进入弃牌堆。若实体牌已在中途被技能获得或转移，原使用事件
的收尾不得再次弃置它。

转化牌仅作为“打出牌”满足响应时，应按父响应事件的打出流程移动，不得因为
复用了转化选择界面而错误建立一次主动使用事件。借刀杀人、青龙偃月刀等规则
文字明确要求“使用【杀】”的响应窗口，必须建立与普通使用【杀】相同的使用
事件，并把全部实体组成牌传递到后续伤害事件。

所有能造成伤害的牌使用入口都必须审计 source_card 与
source_physical_cards。普通单张实体牌可由处理区安全推导一个组成牌，但转化牌
和多实体牌不得依赖该回退；必须由父使用事件显式传递。

群体牌拆分为逐目标无懈、响应和伤害子结算时，每个目标的队列项都必须冻结并
继承同一父使用事件的有效牌面与全部实体组成牌。即使中间插入无懈、判定、濒死
或其他嵌套结算，恢复后也必须继续使用该子结算保存的来源上下文；不得由界面
缓存、动画列表或“有效牌 id → 实体牌”的临时映射反查规则信息。真人与 AI 的
响应成功、放弃响应和无牌响应必须汇入同一来源上下文传递规则。

有效牌面的花色、颜色、点数和类别不得从第一张实体组成牌偷懒继承。除具体牌或
技能另有明确规则外，按官方规则集 3.0 统一处理：

（1）一张实体牌转化为另一张牌时，修改有效牌名和由牌名决定的牌类别，保留该
     实体牌的花色、颜色和点数。例如红色装备牌经【武圣】转化后是基本牌【杀】，
     但仍保留原花色、红色和原点数。
（2）两张或更多实体牌共同作为一张牌时，有效牌没有花色；所有组成牌均为红色
     时有效牌为红色，均为黑色时有效牌为黑色，颜色不完全相同时有效牌无颜色。
（3）多张组成牌的有效点数为各组成牌点数之和；结果大于 K 时按 K 处理。例如
     7 点与 9 点经【丈八蛇矛】组成的【杀】点数为 K。
（4）没有任何实体组成牌的纯虚拟牌没有花色、颜色和点数。若具体规则明确赋予
     属性，则以该规则为准。
（5）颜色判断必须读取有效牌的统一 color 属性，不能用“是否有黑桃或梅花花色”
     代替；因为多实体牌可能没有花色但仍是黑色或红色。

父使用事件必须保存构造完成的有效牌面，例如 SlashEvent.effective_card；防具、
响应、伤害和后续技能必须沿父事件传递这一个牌面。不得在响应、选目标、伤害等
下游分支中重新用第一张实体牌构造虚拟牌。

参考规则：
https://gltjk.com/sanguosha/rules/glossary/gamecard.html
https://gltjk.com/sanguosha/rules/glossary/value.html

14. 新武将/技能的统一接入流程与文档分工

用户约定的新武将或技能接入输入分为三类，三者职责必须分开：

（1）《技能描述.txt》只记录武将资料和技能规则文字，是规则需求来源。
（2）《AI策略.txt》只记录 AI 在真实对局中何时发动、选什么牌、选什么目标、
     如何排序以及何时放弃。用户可以先用不规范的自然语言填写，开发者负责在
     不改变原意的前提下整理成可执行的标准策略。
（3）用户提供的武将语音、技能语音等素材是表现资源输入，不承担规则或 AI
     需求的含义。

《新武将/技能接入流程》属于本《二中杀编程逻辑规范》，不得写入《AI策略.txt》。
《AI策略.txt》中不得混入模块位置、注册步骤、素材整理、测试流程或开发职责。

收到用户要求依据上述输入接入新武将或技能后，开发者必须主动完成：

（1）完整读取《技能描述.txt》和《AI策略.txt》，比较现有武将、技能及策略，
     识别本次新增、复用或修改的内容。
（2）把技能文字规范为精确的时机、条件、次数、区域、目标、可选/强制属性、
     实体牌移动与父子事件关系；能从官方规则和现有代码查明的内容自行查明。
（3）把用户在《AI策略.txt》中填写的口语策略整理为发动条件、材料优先级、
     目标优先级、放弃条件和并列时的稳定排序，并将标准化结果回写该文件。
（4）按本节既定目录创建或复用技能模块，完成唯一 skill_id、注册表、武将数据、
     通用接口以及真人与 AI 共用的合法性校验；不得向 main.py 添加技能特例。
（5）检查用户提供的语音素材，按资源类型和稳定 skill_id 整理到 sound 的统一
     位置，补全音频映射，并保证只有技能实际发动后才播放。
（6）补全规则、AI、取消、超时、非法提交、区域移动、有效牌面、嵌套结算、
     动画与音频资源测试，再运行完整回归测试。
（7）完成后报告采用的标准技能文字、标准 AI 策略、代码与素材位置、规则版本、
     测试结果及仍需用户决定的真正歧义。

开发者整理用户的口语策略时可以修正术语、补足稳定排序和明确放弃条件，但不得
擅自改变用户希望的战术倾向。若两种解释会实质改变选择权、隐藏信息、结算顺序
或战术方向，必须按第十四节的歧义流程询问用户。

15. 失去体力与“替换判定牌”的表现及去向补充

失去体力必须建立独立的体力变化事件，不能伪装成没有来源的 DamageEvent：

（1）直接扣减规则文字指定的体力值，允许角色因此进入0或负体力。
（2）不经过防具或其他伤害增减接口，不触发“受到伤害”“造成伤害”及其后续技能。
（3）体力降至0或以下时仍进入统一濒死、求桃和死亡流程。
（4）界面照常刷新体力显示并播放与失去点数相应的体力减少音效。
（5）不得播放受伤震动、受击位移、伤害字样或伤害来源箭头；这些表现只属于伤害。

技能规则使用“替换判定牌”时，必须同时明确旧判定牌的去向，不能只修改
JudgmentEvent.current_card：

（1）替换牌从技能文字允许的原区域进入处理区，成为同一 JudgmentEvent 的
     current_card。
（2）旧判定牌按照该技能明确的去向移动；若技能规定发动者获得，则从处理区
     公开移入发动者手牌区，不再加入 replaced_cards，也不得在判定收尾时弃置。
（3）旧判定牌已经向所有角色公开，因此获得动画保持正面向上。
（4）后续改判机会和最终判定结果只读取新的 current_card。
（5）最终收尾只处理仍在处理区中的当前判定牌和规则明确仍需弃置的旧牌，禁止
     把已经获得的旧判定牌再次弃置。
（6）替换动画应让新判定牌飞到旧判定牌原先占用的中央等待区位置，再让旧牌从
     该位置飞往其规则去向；不得把新牌排到新槽位而在原位置留下空缺。

16. 规则事件、动画消费与可序列化玩家选择

以下两条是新代码和重构旧代码时必须遵守的强制原则：

（1）新规则只修改引擎状态并产生事件，动画只消费事件。
（2）新的玩家选择都必须能完整表示为“提示ID＋所选牌ID＋目标座次”，并按需要
     附加操作者座次、确定/取消和选项ID；不得依赖界面控件或Python函数表达选择。

具体要求如下：

（1）规则层负责合法性校验、区域移动、体力变化、伤害、判定、技能结果和胜负；
     规则修改成功后发布可序列化 RuleEvent，事件只保存稳定ID、座次、数值和
     公开范围等纯数据。
（2）界面层只能读取已经发生的规则事件来播放飞牌、边框、声音和特效。动画开始、
     结束、跳过或播放失败均不得改变规则结果，也不得决定规则是否合法。
（3）不得在动画结束回调中首次执行扣体力、移动规则牌、冻结判定结果或发动技能。
     旧流程迁移时，应先在引擎中完成规则并生成事件，再把动画回调用于串联表现。
（4）PromptContext 是可发送给客户端的纯数据提示，只保存 prompt_id、
     player_seat、合法牌ID、合法目标座次、所需数量、窗口类型和父事件ID等内容；
     不得保存完整 Player、Python回调、pygame对象或其他不可序列化状态。
（5）真人、AI、局域网客户端和互联网客户端统一提交 PlayerChoice。至少包含
     prompt_id、player_seat、confirmed、card_ids 和 target_seats；需要选择模式
     时使用 option_id。
（6）服务器或本地引擎收到 PlayerChoice 后，必须根据当前活动提示重新校验提示ID、
     操作者、牌所在区域、目标存活状态、合法集合和所需数量。过期、重复或非法
     选择不得推进父结算。
（7）本地客户端可以维护以 prompt_id 为键的界面回调注册表，但该注册表不属于
     PromptContext、GameState 或规则存档，也不得经网络发送。回调只能把已校验的
     PlayerChoice 交给规则接口或继续播放表现。
（8）事件必须带递增 event_id；客户端按编号消费并能忽略重复事件。私人手牌、
     私人选择等事件必须记录接收者座次，不能广播完整隐藏信息。
（9）新技能必须优先返回或发布 CardMoveEvent、HpLossEvent、DamageEvent、
     JudgmentEvent 等规则结果，再由统一表现入口消费；不得在 main.py 中直接为
     技能修改手牌、装备、体力或判定牌。
（10）以上要求同样适用于已经实现的武将技和装备技。修改到旧技能时必须同步迁移，
      不得以“旧代码”为由继续保留界面直接移动牌、直接扣体力或不可序列化选择。
（11）一次操作同时选择牌和目标时，仍只提交一个 PlayerChoice；PromptContext
      必须分别记录 required_cards 与 required_targets，不能把“选牌”和“选目标”
      拆成只能依赖本地界面临时变量的两次非协议操作。

17. 技能文字拆解与结算窗口审计

以后实现或修改任何技能前，必须先把技能描述拆解为明确的规则语义和结算窗口，
再选择已有通用接口或补充新的通用接口。禁止直接按照自然语言表面意思拼接界面
操作，也禁止为了尽快产生相似效果而绕过同类牌、装备或技能已经使用的窗口。

每个技能至少必须明确以下内容：

（1）发动时机：精确到阶段开始时、阶段内、使用牌时、指定目标后、需要使用牌、
     需要打出牌、造成伤害时、受到伤害时、受到伤害后、判定牌生效前等现有窗口；
     相似措辞不得合并为一个模糊回调。
（2）父事件：本技能依附于哪次阶段、牌使用、牌响应、伤害、判定、濒死或其他
     技能事件；技能结算结束后应恢复父事件的哪个节点。
（3）操作主体：谁拥有技能、谁决定是否发动、谁选择牌或目标、谁进行判定、
     谁使用或打出牌、谁获得或弃置牌；这些角色不得因界面操作者相同而混淆。
（4）动作动词：严格区分使用、打出、弃置、获得、交给、展示、亮出、置于、
     视为使用、视为打出、失去体力和造成伤害。相同牌名但不同动词必须进入
     对应的规则事件，不能只检查手牌中是否存在一张同名实体牌。
（5）合法材料与区域：允许选择哪些区域中的实体牌，虚拟牌或转化牌是否可用，
     花色、颜色、点数、数量和牌名如何确定，提交时是否仍需重新校验。
（6）目标与范围：目标数量、是否允许自己、距离或攻击范围、存活状态、阵营及
     多目标顺序；“没有合法目标”与“牌或技能入口不能选中”必须分别判断。
（7）选择性质：技能是锁定、强制还是可选；有多个选项时由谁选择；确定、取消、
     超时和AI提交分别代表哪个规则选项，不能把取消一律解释为结算失败。
（8）成功与失败出口：实体牌响应成功、虚拟牌响应成功、转化牌响应成功、装备
     判定成功、判定失败、主动放弃、无合法牌、目标失效等分支各自进入哪里，
     最终必须恢复或终止正确的父事件。
（9）嵌套窗口：技能文字要求“使用或打出某牌”“进行判定”“受到伤害”等已有
     规则动作时，必须开放对应的完整通用窗口，使八卦阵、转化技、改判技、
     无懈可击、伤害修正、濒死及后续触发技能够按规则介入。
（10）信息可见性：判断只能读取该角色在该时点有权看到的信息。AI不得因规则层
      保存完整状态而查看敌方手牌牌面；未知手牌只能按公开数量或位置处理。
（11）次数与作用域：明确每阶段、每回合、每名角色的回合、每次事件或每个目标
      的限制，并在正确的阶段或事件边界清理。
（12）牌和状态去向：每张实体牌从哪个区域移到哪个区域，虚拟有效牌何时消失，
      回合标记何时建立和清理；动画不得代替这些规则变化。

技能文字出现已有规则术语时，必须复用该术语对应的完整窗口。例如“打出一张
【闪】”不是“从手牌中选一张名为闪的实体牌”：它表示建立一次需要打出【闪】
的响应窗口，因此实体【闪】、合法转化牌以及八卦阵等“视为打出【闪】”效果都
必须能够介入；响应成功后还要产生统一的成功打出事件。若技能规定“不打出则
执行另一项”，主动取消、超时、无牌和所有合法响应方式均应汇入该技能明确的
失败出口，而不是沿用【杀】的伤害分支。

实现前应形成一份最小窗口表，至少包含“时机、父事件、操作者、输入、合法性、
成功出口、取消/失败出口、可插入的子窗口、恢复点”。能被现有窗口完整表达时
必须直接复用；现有窗口缺少通用成功或失败出口时，应扩展通用接口，不得在
main.py 中按技能ID或技能名增加分支。

主动转化牌不得只支持【杀】或无目标牌。转化后的有效牌需要目标时，提示必须
同时携带合法材料牌ID与合法目标座次；提交后按有效牌名进入与实体牌相同的目标
合法性、无懈可击、选牌、伤害和结算后窗口。中央等待区只展示实体组成牌，虚拟
有效牌只保存在规则上下文中。

“因某牌被弃置”必须建立保存操作者、目标、有效牌名、被弃置实体牌和牌移动ID
的因果事件，不能只凭弃牌堆中的最终位置或 reason 字符串猜测。“此牌结算后”
必须在全部目标及子窗口完成、实体组成牌确定最终去向后开放；“出牌阶段结束时”
必须在冻结本阶段使用牌统计后、进入弃牌阶段前开放。下个摸牌阶段奖励只在角色
真实进入摸牌阶段时消费，被跳过的摸牌阶段不得清除奖励。

任何触发技、选择目标或选牌询问临时覆盖父响应窗口时，必须完整保存并在技能
序列结束后原子恢复父窗口的 prompt_id、操作者、来源角色、所需牌名、来源牌、
响应动作、成功/失败出口及剩余时间。没有父窗口时必须恢复为空闲状态，禁止让
“默认需要闪、默认来源杀”等字段被误当成真实规则事件，否则会产生技能结算后
错误要求角色对自己响应【杀】之类的串线。

角色规则身份以稳定座次或稳定角色ID判断，不以 Python 对象是否为同一实例判断。
状态快照、序列化重建对象和原状态对象只要座次相同，就必须视为同一角色，不能
互相成为【杀】、【决斗】、【过河拆桥】等禁止指定自己的牌的目标。

锁定技的常驻技能框使用素材目录中 compulsory 类型的带锁按钮，并保持普通态
显示；它不是灰暗的主动技按钮，也不能进入点击命中或“是否发动”询问。主动技、
限定技和阵法技分别使用 proactive、oneoff 和 array 类型素材，按钮外观不得反过来
决定规则是否可发动。

测试必须覆盖文字拆解得到的不同语义分支，至少包括实体牌、合法虚拟或转化牌、
相关装备技能、取消、无牌、超时、目标或材料中途失效及父事件恢复。只有画面上
出现了相似结果，不代表技能已经按正确窗口实现。
